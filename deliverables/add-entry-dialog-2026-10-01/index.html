添加内容窗口（Memo / 待办）· 优化方案

优化 Memo 页 / 待办页右上角「添加」弹出的添加内容窗口。左是现状（已落地 v1）， 右是方案（已按 D1–D4 定稿）。两个弹窗都能真输入、真发布，用来对比手感，不只是静态图。

01现状 vs 方案（可交互）

说的是 Memo 页 / 待办页右上角那个「添加」弹出来的窗口，不是功能栏里的快速录入框—— 那边一个字都不动。两边的弹窗都可以直接输入、点清单 chip、点标签、点发布。 页首「在 Memo 页 / 在待办页」两个按钮用来模拟你从哪个页面点的添加（D1 已定类型由页面决定，窗口内不切换）。 颜色 / 字号 / 圆角 / 间距全部取自 DESIGN.md 令牌，右上角可切深色。

现状 已落地 v1 打开即定位；类型锁死在打开时那一次
方案 清单 Memo 也能设截止与优先级 · 标签可点选 类型由所在页面决定，窗口内不切换

02按 D1–D4 定下的方案

你已定：D1 不放类型切换、D2 清单仍需点确认、D3 放宽窗口、D4 发布即关窗， 以及「窗口可以做大一点，属性区两行三行都行」——据此定为 520px + 属性区三行。 加上「页头入口」这个口径澄清（不是在功能栏录入框里加东西），最终形态是下面这六条。

1类型由所在页面决定，窗口内不放切换

入口是 Memo 页 / 待办页右上角的「添加」，你在哪个页面，类型就已经定了； 窗口里再摆一个 Memo/待办 切换等于让用户改自己刚做过的选择。原型页首那两个按钮就是模拟 「你在哪个页面点了添加」。

好处
kind 依旧由打开入口决定，Modal 公共组件不用改（原先要加头部插槽）。
保持
Ctrl+N 仍默认落在 Memo 档。

2Memo 确认为清单后，截止 / 优先级跟着出来

这是本轮最实的一条。清单 Memo 就是 is_task=1，而待办视图取的正是 is_task === 1——所以你在 Memo 页点完「设为清单？」的下一秒，这条就已经躺在待办视图里了。 但现状里字段行只剩一个 chip，没有任何地方能设截止和优先级，用户只能去待办视图再改一次。

根因
publishMemo 的 options 本来就收 due / priority， 是 AddEntryDialog 只传了 { asTask }，把它们丢在窗口里。
成本
零协议改动：字段、写入通道、md front matter 全都现成，只补 UI 与一个 prop 形状。
控件
与待办档同一族：截止用原生 date、优先级用盒式分段控件，不新增控件形态。

3标签：从「只能靠正文 #」变成可点选

现状标签由 deriveTags(text) 从正文 # 派生，窗口里没法点、也没法看全。 而 tags 是 Memo 侧栏筛选、标签视图、待办筛选都在吃的字段。

做法
字段行给一个「+ 标签」chip，点开是锚在旁边的短菜单（§5.3 短菜单走菜单浮层，不是弹窗）： 已有标签多选 + 输入新建。
与正文 # 的关系
两边的标签合并去重后一起写进 tags；正文里来的显示为紫色、点选的显示为橙色，来源一眼可分。
边界
标签写进元数据，不写进正文（沿用既有约定）。

4字段行不再有「空行」，但清单仍需点确认

字段行固定 26px 不许塌陷（发布时不跳高度），但 memo 档在没写 - [ ] 时原本是 纯空白的一条。现在这行常驻一个「清单」chip 占位（不可点、无清单项时不误导）， 写出 - [ ] 后它变成可点的「设为清单？」。

D2 口径
不自动勾：写了 - [ ] 只是问，点一下才变清单（守住需求 §9.3）。
行尾
清单项数量「N 项」实时可见（§5.4-2 实时计数必须可见）+ 一个 ⓘ 说明 @ 与标签口径。

5记录日期：这条落在时间轴的哪一天

Memo 时间轴按 memo_at 分天，现状写死 memo_at: now——所以现在 只能记"此刻"，补记昨天、提前记明天都做不到。加一个日期字段就补上了这个缺口。

形态
字段行最左侧一个 sw 胶囊：日历图标 + 今天（默认）或 10-01（改过）。 选了非今天就转主色，一眼看出"这条会落到别的一天"。
默认
留空 = 今天 = 现状行为，一个字都不改时发出去的 memo_at 与现在完全相同。
只给 Memo 档
待办档已有「截止」，再加一个"记录日期"会让同一行出现两个日期、含义打架。 待办不做——要记哪天，用 Memo 记。
控件
胶囊里套一个铺满但透明的原生 <input type="date">：点 chip 弹系统选择器、 键盘也能直接聚焦。比 showPicker() 稳；不用 display:none（不可聚焦）。

6窗口放宽到 520px + 属性区分三行

D3 定了要放宽；你随后明确「窗口可以做大一点，两行三号（行）都可以」，据此定为 520px + 属性区三行。落地方式仍是只改这一个窗口：DESIGN.md §2.2 的 「弹窗最大宽 400px」保持不动，另加一条结构尺寸「添加内容窗口宽 520px」—— 解锁、重置密码、定义列结构那些弹窗不受影响。

三行分组
行 1「这条是什么」：记录日期 · 清单标记 · 清单项计数 ｜行 2「什么时候」：截止 · 优先级 ｜行 3「归到哪」：标签
空组不占位
这一条改了 §2.2：原来是「固定 26px、不换行、空行也占位」， 现在按需出现——待办档不会出现一条什么都没写的行。
发布不跳高
原规则要占位，本质是怕发布时高度变。现在发布不改任何内容，高度稳定； 唯一的变化是用户主动点「设为清单？」展开行 2，那是有意展开。
顺带
输入区 96 → 112px；行内允许换行，标签多时往下长而不是横向拖。
禁用原因
空内容时「发布」置灰的原因从 title（键盘/触屏看不到）挪到输入区下方一行可见 micro 提示， 修掉 DESIGN.md §6.1「禁用必须说明为何禁用」这条违反。

03属性配置：数据层允许什么

逐条对着 packages/shared/src/items.ts 的 ItemMeta / ItemWriteMeta / ItemMetaPatch 与 useMemoWrite.ts 的写入路径核过。分界线是 「新建时能不能写」——只有 patch_meta 支持、新建协议里没有的字段，这轮不做。

做

标签 tags

tags: string[] 在 ItemWriteMeta 里，新建即可写； patch_meta 也支持。窗口点选的标签与正文派生的标签合并后一起落库。

做

截止 task_due / 优先级 task_priority（清单 Memo 也给）

两个字段都在 ItemWriteMeta 里，publishMemo 也已经透传。 待办档常驻；Memo 档在确认为清单后出现——因为那就是一条真待办。

做

记录日期 memo_at（只给 Memo 档）

memo_at 在 ItemWriteMeta 里，新建即可写；现状被 publishMemo 写死成 now，改成接受一个日期即可。 实现上有个坑：memo_at 是毫秒时间戳，而时间轴分天走的是 设置时区（groupMemosByDay 默认 Asia/Shanghai，不是本机时区）。 我的建议是只改年月日、保留当前时分秒，并按设置时区构造——这样补记的 Memo 在那组里 排在最新位置、显示的时间也正常；直接写当天 00:00 会让一堆补记条目都显示 00:00。

不做

状态 task_status

值域 todo / doing / done，但新建默认就是「待办」，发布后再改比发布时选更自然， 而且待办视图本来就有拖动 / 点选改状态。放进添加窗口只是多一个几乎不用动的控件。

不做

置顶 pinned / 收藏 starred

这两个字段只在 ItemMetaPatch 里，ItemWriteMeta 没有—— 要在新建时设置就得扩协议（服务端与客户端的 schema 一起动）。而且刚建的条目置顶 / 收藏价值很低， 收益配不上改协议的成本。

不做

单篇加密 enc_self / 放进加密空间 in_enc_space

服务端在 ItemMetaPatchSchema 里明确拒绝给 Memo 做单篇加密（Memo 归隐私锁管）； in_enc_space 必须和 folder_id 同一次补丁给，且隐私锁关闭时不可用。 设计文档 §8.7 也定了「输入框没有加密开关」。

待定

所属笔记本 / 文件夹 folder_id

技术上完全支持（ItemWriteMeta.folder_id 就在那儿），但有两个顾虑： 一是 Memo / 待办都是全局视图、「这条属于哪个笔记本」的实际诉求不强； 二是要引入文件夹树选择器这种重控件，塞进这个窗口里很挤， 还得处理加密空间内的文件夹在锁着时不可选。 我的建议是这轮不做，真要归档，建完再拖更顺手。你若觉得随手归档有价值，我再单独出一版。

04还需要你点头的两件事

D1–D4 已定，这两条是属性配置带出来的新问题。

N1

标签这一项，做还是先不做？

它是本轮唯一需要动「标签从哪来」这条既有口径的改动（从纯派生变成派生 + 点选合并）。

已定

N1 · 标签做（2026-10-01 拍板）

字段行给「+ 标签」chip → 锚在旁边的短菜单（已有标签多选 + 输入新建）， 与正文 # 派生的标签合并去重后一起写进 tags。 正文来的显示紫色、点选的显示橙色，来源一眼可分。属性一律不写进正文。

N2

520px 是只给这个窗口，还是改全局弹窗宽度？

改全局最省事，但解锁、重置密码、定义列结构那些弹窗会一起变宽，属于没必要的连带改动。

已定

N3 · 属性区分三行（2026-10-01 拍板）

你说「窗口可以做大一点，两行三行都可以」，据此定为 520px + 属性区三行，按 「这条是什么 / 什么时候 / 归到哪」分组。这会改 DESIGN.md §2.2 的 「添加内容窗口字段行高 = 固定 26px、不换行」——改成「属性区每行 min-height 26px、 允许换行、空组不占位」。这是本轮唯一一处推翻已定结构尺寸的地方，实施时要单独回写。

05两个入口怎么弹 · 复用盘点

「待办右上角的添加」已经在弹同一个窗口了——不是要新建一个。两处入口都走 addEntry.open(kind)，同一个 useAddEntrySlot、同一个 AddEntryDialog，只有 kind 不同。原型页首那两个按钮就是它的模拟。

✓已经真正共用的（保持）

这些是两个弹窗（乃至两个录入面）之间实打实共享的东西，实施时一份都不许抄第二遍：

窗口装配
useAddEntrySlot（App/AddEntrySlot.tsx）——开关状态 + JSX 一份， 两个入口都指到它。App.tsx：待办 onAdd → open("task")， Memo onAdd → open("memo")。
窗口本体
AddEntryDialog 一个组件、kind 两种——这正是你最初要的 「复用一个窗口结构、只换显示的设置」。
判定与文案
TASK_ITEM_PATTERN（- [ ] 清单项）、TASK_PRIORITIES / TASK_PRIORITY_LABELS（来自 @menote/mdcore）、deriveTags、 deriveTaskFields——都是共享纯函数，不在本窗口重写。
写入
publishMemo 一条路径（useMemoWrite.ts）， onPublishTask 就是它的 { asTask: true, ...options } 包装。
UI 与时区
Modal / Button / Chip / SegmentedControl / InfoHint；dayKeyInZone（memos/model.ts）分天， 记录日期的反向换算（新函数）放同一处、同样带单测。

!名存实亡的"复用"：ModeExtras

现在的字段组件 ModeExtras 挂在 Composer.tsx 里、注释写着 "两个录入面复用同一份实现"。但它已经只有一个调用方了—— 功能栏录入框 2026-10-01 把属性行删掉之后，Composer.tsx 里根本没有渲染它。

证据
全仓 ModeExtras 只有一处 import：AddEntryDialog.tsx。 Composer.tsx 的 JSX 里只有 QuickComposer + composer__modes。
为什么不该继续硬复用
它的形态与新方案对不上：① 参数是 mode: ComposerMode 的三分支 if/else， 其中 note 档分支对窗口毫无意义（笔记不进这个窗口）； ② 死守单行 26px，而这轮已定三行；③ 要加记录日期与标签，都塞不进去。
建议
把它收成窗口自己的 AddEntryFields（放 fnbar/ 下、只服务窗口）， 顺手把 Composer.tsx 里那几处只为它存在的导出与注释清掉—— 真正的共享（TASK_ITEM_PATTERN、ATTRIBUTE_FOCUS_SELECTOR）留在原处。
影响面
零行为变化，只是把「假装被复用」的组件搬回它唯一的使用方旁边； add-entry-dialog.test.tsx 的 13 条用例按新结构改断言即可。

06本轮明确不做

  • 功能栏录入框：这次只改 Memo / 待办页头「添加」弹出来的窗口，功能栏那个快速录入框一个字不动（2026-10-01 刚把它压回两行）。
  • 笔记档：新建笔记仍走功能栏「新建笔记」，窗口只服务非笔记类（沿用已定口径）。
  • 图片 / 附件：瀑布流只渲染带图 Memo，窗口里加图会重现「加了看不见」。
  • 富文本：仍是 Markdown 纯文本，属性一律不写进正文。
  • 待办档的记录日期：待办已有「截止」，同一行再放一个"记录日期"含义会打架。要记哪天用 Memo 记。
  • 发布后不关窗的连续记录：D4 已定发布即关窗。
  • 窗口内类型切换：D1 已定不放。
