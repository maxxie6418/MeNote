## 📌 TL;DR

- **整体结论：🟡 有条件通过**。架构主线（胖客户端/瘦服务端、本地优先、条件写、单 Worker 同源、单一 Cron 分派）在 Cloudflare 免费版上是成立的，接口与表结构草案的完成度约 80%。
- **阻塞项 9 条**（🔴）：其中 3 条属于"需求已定但架构无落点或自相矛盾"（非对称密钥对缺失、分享查看器路由、密文/密钥实现矛盾），4 条属于"照文档朴素实现即出错"（Cron 配额超限、`sync_seq` 批内重复导致同步漏拉、`attachment_refs` 主键含 NULL 失效、R2 GC 误删在用对象），2 条是安全架构级缺陷（备份明文外泄/SSRF、`deviceKey` 跨户串用）。

## 1. 各成员核心结论

### 🔍 产品评审员（合理性与完整性）
- **核心判断**：结构良好、标注体系（依需求/架构定/待确认/待核实）清晰，但**不能直接照着写代码**。头号问题是"覆盖缺失"：全篇没有非对称密钥对，而功能拆解 M08-09 已明确要求"账户增加一对非对称密钥：公钥明文存储、私钥用主钥 MK 包裹"，并写明"密钥对何时生成由架构文档确定"（功能拆解 L546–549）；§7.4（架构 L491）还写成"中断后在**下次解锁时**继续"，与 M08-09/M08-11"锁定态移入**不依赖解锁**"直接矛盾。
- **关键建议**：补 §7.x 密钥对设计；分享查看器路由二选一写死；补 6 个缺失章节（可观测性与告警、客户端存储持久化、附件 20MB 上限、域名/部署/回滚、实例用量口径、备份恢复路径）；把纯技术选择从【待确认】降为【架构定】+ADR（用户无法裁决这些）。

### 🔧 调查员（免费版工程可行性）
- **核心判断**：整体自洽度中上，§19.1 限额抄录基本准确，R2/D1 一致性机制（先登记 → 写 R2 → 同 batch 提交）与 D1 `batch()` 单事务语义成立；但**4 处照朴素实现就会出错**：`sync_seq` 批内重复叠加 `LIMIT 200` 会永久漏拉；`attachment_refs` 用可空 `version_id` 进主键在 SQLite 中唯一性失效；`r2_gc_queue` 的 `pending_upload` 过期清理会误删仍被引用的去重对象；Cron 每轮语句数约 96 条 > 免费版 50 条上限。
- **关键建议**：给出一组可直接照抄的修正数值（见第 5 节）；把"密文列类型"在架构正文复述（设计文档 §18.2 的 `body` + `body_enc` 双列是对的，但架构正文没写，实现极易把密文走 `text()`）；CI 补 4 项门禁。

### 🛡️ 安全官（OWASP + STRIDE）
- **核心判断**：无典型 SQLi / 存储型 XSS 直接缺口（正文一律参数绑定、渲染经 DOMPurify、`frame-ancestors 'none'`）。但有 4 个架构级真缺陷：①"所有 CryptoKey `extractable:false`"与 AES-KW `wrapKey()` 的硬性矛盾（按字面实现加密根本启用不了）；②分享查看器与主应用同源同 SW 作用域，任一分享页 XSS 即升级为账户接管；③外部备份把明文笔记/Memo/附件上传第三方，且备份目标 URL 用户可配 → SSRF，凭据单密钥无轮换；④`deviceKey` 单行无 `userId` 归属，多用户共用设备会跨户串用密钥。
- **关键建议**：密钥改"双对象"生命周期（可导出仅存在于包裹瞬间，运行时全 false；MK 作包裹钥只需 `wrapKey/unwrapKey` 用途、**不必可导出**）；分享查看器迁独立 origin/子域 + `COOP`；备份增加端到端加密选项 + 目标 URL 允许列表；`deviceKey[userId]` 分区并在登出/切户清除。

## 5. 可直接照抄的修正数值 + 必测清单

### 5.1 修正数值（免费版安全上限）

| 项 | 建议值 |
|---|---|
| Cron 每轮 D1 语句总数 | **≤35**（硬上限 50，含中间件与 `users` 读） |
| Cron 每轮 R2 对象操作 | ≤50（删除免费；内部额度 1,000） |
| 外部子请求/轮 | 备份 Git **≤30 文件**（≈34 子请求）；S3/WebDAV 镜像 ≤20 文件 |
| 同时出站连接 | ≤6 → 备份/离线预取**并发 ≤4** |
| `GET /api/sync` | **所有类型合计 ≤200 行**（非每类 200） |
| `POST /api/batch` | **≤35 语句**（含鉴权 SELECT） |
| `X-Menote-Meta` | 软限 **≤64KB**；附件引用 >200 条改独立请求 |
| Cron 配额改写 | 1（注册）/ ≤2（GC，IN 批量）/ ≤2（快照）/ ≤3（idle）/ ≤2（备份）/ ≤2（维护）条语句，任务**轮转**执行 |
| 构建门禁 | Worker 未压缩 ≤64MiB；静态资源文件 ≤20,000；单文件 ≤25MiB；首屏 JS ≤200KB（已有） |
| 收尾游标 | `(sync_seq, id)` 元组 + `ORDER BY sync_seq, id` |

### 5.2 必须早期实测（构造用例）

1. **子请求归属**：同一 Worker 内循环 `fetch()` 外部 + `R2.get()`，二分找出各自失败点（判定内部服务是否独占 1,000 额度）。
2. **batch 语句计数**：一次调用发 60 条小语句，观察是否在第 51 条报错。
3. **1.9MB 全文/整篇**：`text/markdown` 与 `application/octet-stream` 各压一次，读 Workers 日志 CPU；对比 `request.text()` vs `arrayBuffer()` 读密文是否损坏。
4. **D1 BLOB 往返**：`INSERT ... VALUES(X'00FF..')` → `SELECT` 看返回类型；把 `Uint8Array` 绑到 TEXT 列验证是否被 UTF-8 破坏。
5. **静态资源路由**：部署 `run_worker_first` 数组，验证 ① 浏览器导航 `/api/x` 命中 Worker；② `/s/abc` 是否返回 index.html；③ 资产请求在日志中无 Worker 调用。
6. **请求头边界**：`X-Menote-Meta` 发 50/100/130KB，找 413/431 阈值。
7. **D1 单库竞争**：5 客户端并发写，观察 `overloaded`。
8. **`RETURNING`** 与 **`json_each`(1000 元素) + IN(100 参数)** 可用性。
9. **MCP 512KB 小节解析**、**服务端 256KB gzip** 的 CPU。
10. **Cron 全轮**：6 任务全开跑一轮，读 CPU 与语句/子请求错误。
