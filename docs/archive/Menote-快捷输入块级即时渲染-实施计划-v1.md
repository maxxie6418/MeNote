## 1. 问题定位（先看清楚，别改错地方）

`apps/web/src/app/fnbar/QuickComposer.tsx` 的现状是**两态**：

```ts
const showView = !editing && value.trim() !== "";   // 第 124 行
```

- 聚焦时整块就是一个原生 `<textarea>`；
- **只有失焦**（且内容非空）才整块换成 `MarkdownPreview` 只读呈现。

于是用户观察到的两件事都是必然结果：

1. **换行（Enter）不会呈现**：仍在校验态里，`editing` 还是 `true`。
2. **`/加粗` 之后看不到效果**：`applyFormatAt()` 只改了 textarea 的文本（`**加粗**`），呈现时机仍然是"失焦"。

设计稿 `docs/modules/Menote-编辑拓展-设计-v3.md` §一-3 原文允许三个时机——"**完成当前块**、失焦或查看时能按 Markdown 语义呈现"——实现只取了**最弱的一个**（失焦）。验收清单（已归档的实施计划 §7）那条也写成"写完一段，**点别处** → 内容按 Markdown 呈现"，所以它"通过"了。**这是验收标准定得太低，不是实现偏离得离谱**；本稿把标准改回设计原意。

## 2. 方案（用户 2026-09-30 选定 A）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（选定）** | **块级即时渲染**：内容按 Markdown 块切分，**当前块是 textarea（保持源码）**，其余块即时按 Markdown 呈现；Enter / 光标离开即提交当前块 | 真"所见即所得"，符合设计原意；代价是 `QuickComposer` 重写、跨块撤销变弱（见 §5） |
| B | 保留单 textarea，下方加一条实时预览 | 改动最小；但输入区与预览区文字重复，功能栏变高 |
| C | 只在光标离开当前行时呈现那一行 | 介于两者之间；列表内换行手感糙 |

**B/C 不采用**，理由记录在此以免以后重开讨论：B 的"同一段文字看两遍"在 40–180px 的录入框里不可接受；C 会在列表里出现"上一项已呈现、下一项还在源码"的错位观感。

## 3. 交互规格（实现的唯一依据）

### 3.1 块怎么切（纯函数 `splitQuickBlocks(text)`）

按 Markdown 的块语义切，**必须与整篇渲染的结果一致**，否则会出现"呈现后和原来不一样"：

- 块 = 极大的连续行段，以下情况**开新块**：
  1. 行首是块级标记：标题 `#{1,6} `、引用 `> `、无序列表 `[-*+] `、有序列表 `\d+[.)] `、围栏 ` ``` `（含 `~~~`）、分隔线 `---`/`***`/`___`；
  2. 前一行是空行（空行本身归**前一块的尾部**，不单独成块）；
  3. 围栏内：从开围栏到闭围栏（含）算**一块**，围栏内的 `#`、`-` 等不作标记（代码块里不切）。
- 其余连续行（含表格行、续行）留在同一块——CommonMark 的 lazy continuation 语义：`- 项目\n续行` 是一块，不是两块。
- 返回 `{ from, to, text }[]`（`from`/`to` 是行下标区间），**纯函数**、不依赖 DOM，单独测。

### 3.2 编辑态

- 当前块渲染成 `<textarea>`，**其余块**（前、后都算）渲染成只读呈现块。
- **当前块的值就是该块的源码**：textarea 的 `value` = `blocks[active].text`，`onChange` 把该块替换回全文再交给宿主（宿主契约不变：`value` 仍是全文）。
- **Enter**：插入 `\n`。若因此切出新块，当前块自动落到新块（textarea 的 `value` 变成新块源码、光标落到开头）——上一块**当场呈现**。这是本次缺陷的直接修复点。
- **Shift+Enter**：软换行，留在当前块（同 Markdown 的软换行语义）。
- 光标落在哪个块，哪个块就是当前块（点已呈现的块 → 那块变成 textarea 并获得焦点；光标落点取该块末尾）。
- 一次只有一个 textarea；在块列表里用稳定 key，**React 必须复用同一个 DOM 节点**（换块时不能重建 textarea，否则焦点、输入法组合、原生撤销都会断）。
- `/` 与 `@`：判定与执行都在**当前块的局部文本/局部光标**上做（比现在的全文偏移简单）；`applyFormatAt()` 与 `triggerAt()` 仍用共享实现，不吃第二份规则。
- 输入法：组合期间一律不切块、不呈现（`isComposing` / `compositionstart` 期间 Enter 交给输入法）。
- 失焦：焦点离开整个录入面（`keepEditingWithin` 之外）→ **全部块呈现**（保留现状作为兜底，`showView` 语义不变）。

### 3.3 视觉与布局

- 复用现有类名语义：输入态仍是 `.composer__input`（功能栏）/ `.addentry__input`（添加内容窗口），呈现态仍用 `.quick-composer__view`；新增块容器类名走 `style-coverage.test.ts` 的"每个 className 必须有 CSS 规则"约定。
- 呈现块的可点区域必须**键盘可达**（`role="button"` + `tabIndex={0}` + 可见焦点环），与现有 `.quick-composer__view` 一致；不得只靠鼠标悬停或点击。
- 高度：功能栏录入框仍守 `layout-invariants.test.ts` 的 40–180px 与 `resize: vertical`；块列表超出时**容器自己滚**，不把功能栏顶高（`DESIGN.md` §2.6「每层一个滚动容器」）。
- 不改导航 y=252 等结构不变量，不改任何色值与字号（视觉源只有 `DESIGN.md`）。

## 5. 已知取舍（写清楚，不藏）

1. **跨块撤销变弱**：原生 `Ctrl+Z` 只作用于当前块的 textarea；跨块（"撤销上一块刚提交的改动"）不保证。缓解：宿主本来就在发布/持久化时落库，撤销不是主要防线；若后续要补，另开一条"块级撤销栈"任务。
2. **块切分是近似**：以 CommonMark 的块边界为准，但不实现 setext 标题、缩进代码块、GFM 表格跨行等边角；遇到罕见写法时表现为"呈现时机分块稍有不同"，**不会改内容**（内容永远是 `blocks.join("\n")` 的原文）。
3. **点击已呈现块的落点**取该块末尾，不按鼠标坐标定位。

- [ ] **`/` 立刻可见（按真实动作）**：打 `/加粗` → 菜单回车（光标落在 `****` 中间）→ 接着打字 → `Enter` → 这一块**不点别处、不失焦整个录入框**就按粗体呈现。
  - 注意：**不存在"先选中文字再打 `/加粗`"这条路径**——打字会替换掉选区（计划 v1 原写错了，见 §9-3）。要"给已有文字加粗"目前只能手工补 `**`，或用正文编辑器的工具条。
  - **时机口径（用户 2026-09-30 拍板，设计稿 v3.4）**：`/` 的结果是**提交该块之后**呈现。当前块保持 Markdown 源码，所以按完菜单先看到 `****` / `- ` 本身，这是设计要的样子，不算缺陷。
- [ ] **任务清单按场景给**：待办与 Memo 档的 `/` 菜单里有「任务清单」，选中插出 `- [ ] ` 且光标在后面；笔记快捷录入的 `/` 菜单里**没有**这一条。
- [ ] **段落软换行（已知取舍）**：在一段话里 `Enter` 会先呈现上一行，接着写第二行时两块并回同一段、呈现让位给源码（Markdown 语义如此）；内容一个字不差。
- [ ] **点回编辑**：点任意已呈现块 → 那块变回源码、焦点落进去、内容一个字不差；改完 `Enter` 又呈现。
- [ ] **失焦兜底**：整段写完点页面别处 → 全部块呈现；点回来能继续编辑。
- [ ] **中文输入法**：组合期间不切块、不呈现、不抢 Enter；上屏后再 `Enter` 才提交该块。
- [ ] **列表连续回车**：`/无序列表` → 打字 → `Enter` → 新行仍是列表项（或按设计退出列表）；连按两次 `Enter` 得到空行/退出。
- [ ] **高度与滚动**：内容变多时录入框仍在 40–180px 内、自己滚，功能栏与导航位置不走样。
- [ ] **添加内容窗口**：Memo 与待办两个 kind 里行为与功能栏一致；`Ctrl/Cmd+Enter` 仍发布、发布后清空回到输入态。
- [ ] **不回退**：`@`（待办截止/优先级）、代码块内的 `/` 不弹菜单、发布 toast 与列表刷新都仍然正常。
- [ ] **正文默认档**：清掉本机"上次用的那一档"后打开一篇笔记 → 直接是**即时渲染**。

## 8. 教训（写给下一次的自己）

1. **设计稿里的"或"是陷阱**：原文写"完成当前块、失焦**或**查看时"，实现选了最省事的那个。写计划时应当把**必须成立的时机**写成硬要求，把"或"留给真正的可选路径。
2. **验收项要写成"用户动作 + 可观察结果"**，且动作必须覆盖**打字过程中**；"写完一段点别处"这种验收天然测不到打字时的呈现。
3. **不能把"自动化全绿 + 一句话口头确认"当成验收**：这次 1404 条用例全过、清单也"看着满足"，但用户第一眼用就发现两条不成立。以后交付同类改动，必须给出可逐条勾选的清单，并由用户勾。

## 9. 实施结果与三处"计划与实现不一致"（v1.1，2026-09-30）

1. **切块模型改了一处**（计划 §3.1 原本写"空行归前一块"）：**文末那个空行必须自成一块**。否则用户按下 Enter 后文本是 `…\n`，那一行被并进前一块，列表里回车就不会把上一项交出去呈现——**正是用户反馈的场景**。中间的空行仍归前一块（Markdown 语义），两种规则并存，安全网用例（`join("\n") === 原文`）覆盖两者。
2. **无标记的连续两行同属一段**：所以段落里按 Enter 会先呈现上一行，接着写第二行时两块并回一段、呈现让位给源码。内容不变，属已知取舍（已写进代码注释与 §7）。
3. **§7 原来那条"/ 立刻可见"的动作不成立**：`applyFormatAt()` 在**空选区**上插入一对标记（`****`）并把光标放中间，用户接着打字。要是先选中文字再打命令，打字会替换掉选区——所以"选中文字 → `/加粗`"根本不是一条可达路径。已按真实动作改写验收项，并在 §7 注明"给已有文字加粗目前只能手工补标记"（要加"选中文字加粗"的入口，得另立一个小任务，不在本计划范围）。
4. **样式文件路径**：计划写 `apps/web/src/app/app.css`，实际是 `apps/web/src/app/theme/app.css`。
5. **验证数字**：web 全量 1101 通过（改造前 1058）；首屏 gzip 186.4 KB（改造前 185.4）；`pnpm lint` 0 error（1 条既有 warning）；typecheck 0 error。
6. **未验证（等用户逐条勾 §7）**：真实浏览器与中文输入法的点验、触屏命中区与窄屏表现、长 Memo（多块）时的滚动与性能。
