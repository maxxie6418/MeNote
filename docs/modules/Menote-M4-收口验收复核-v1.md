## 五、偏离与实现选择（14 处，均已在对应文档或代码注释登记）

1. **版本历史用"主操作区独立面板页"**（界面稿默认取舍已采纳）：理由是弹窗最大宽 400px 装不下并排 diff，而给 `DESIGN.md` 加"宽弹窗"档属改视觉源。
2. **保留密度只读**：设置页只开放条数与最长时长，密度按定稿规则展示。
3. **「标记为保留」可取消**（界面稿默认取舍）。
4. **永久删除确认框不提"快照文件"**：正文只写"条目 + 全部版本 + 不再被引用的附件"与"不可撤销"。
5. **正文里的附件引用写法由本程定稿**：图片 `![名](/api/attachments/h/<sha>)`、非图片 `[名](…)`——预览不用自定义语法、客户端一条正则抓全引用、缩略图只是渲染时加 `?thumb=1`。
6. **缩略图在浏览器生成**（设计 §十-1 的默认）：否决架构 §八 的 `media.worker`。
7. **附件管理页留 M6**（设计 §十-2 的默认）：M4 只做接口 + 元数据 + Cron。
8. **`StorageEnv` 收窄**：服务层只依赖 `DB` + `ATTACHMENTS`，不拿整个 `EnvBindings`。
9. **表格的一处退化**：**主动降级**（「降级为普通笔记」）——确认框已按界面稿写全三段，但**按钮禁用并写明原因**：它要把 `items.type` 从 table 改成 note，而 `ItemMetaPatchSchema` **不允许改 type**（属接口变更，见 §七-11）。此前登记的另两处已在收口期间补齐：**标签列 chip 编辑**（v0.4.30，存储仍是逗号分隔字符串）与**行拖动排序**（v0.4.30，键盘等价入口是行菜单的上移/下移）；**"自动降级提示条"**在 v0.4.26 补上。
10. **附件引用只在"上传时"上报**（`finalize(itemId)`）；**编辑后再对齐引用**需要条目保存携带引用集合（要改 items API 请求结构），留 M6 与附件管理页一起做；期间由**孤儿 30 天规则**兜底。
11. **`wrangler.jsonc` 的 `r2_buckets` 与 `triggers.crons`**：用户 2026-09-27 确认 R2 后落地；绑定名统一为 `ATTACHMENTS`。
12. **新增 `fnbarWiring`**（从 `App.tsx` 抽出）：把"从独立页回笔记区"这条规则收成一处，App 已顶到 500 行预算。
13. **回收站列出文件夹**（v0.4.28 补）：界面稿 §6.5 要求文件夹也出现在回收站里；实现为"条目 + 文件夹"两张查询在模型层合成一张列表，恢复按 kind 分流（文件夹走 `restoreFolder`）。同批登记一条遗留：**文件夹的永久删除服务端还不支持**（见 §七-12）。
14. **两条审计手段**（见 §八）：调用点检查（非测试的调用点为零即未接线）与端到端可达性（从 `main.tsx` 沿静态 + 动态 import 递归），以及"服务端端点逐个查测试覆盖"。这是被 M4 期间四次"写好了没接上"逼出来的。

11. **是否允许「降级为普通笔记」改 `items.type`**（table → note 单向）：`ItemMetaPatchSchema` 现在**不允许改 type**。不给这个能力，结构损坏的表格就只能永远以"降级视图"打开（能看能改正文，但类型一直是 table、列表图标也不对）；给的话要扩一个"类型单向变更"的补丁字段。**建议做**。

## 八、审计方法与结论（2026-09-27 新增）

### 8.1 为什么加这一步

`lint` / `typecheck` / `test` 全绿**不足以保证"做完了"**——M4 期间连续抓到四次
"模块写好了、单测也过了，但在应用里没接上或接错了"：

| # | 发现 | 后果 | 修复 |
|---|---|---|---|
| 1 | `routes/versions.ts` **没挂载**到 `index.ts` | 版本历史的五个端点在线上全 404（单测直接打服务层，所以没暴露） | v0.4.19 |
| 2 | **表格从没接进正文区**：`TableEditor` 与 `checkDegrade` 在 `apps/web/src` 里零调用点 | 打开表格条目看到的是普通 Markdown 编辑器（57 例全绿也没用） | v0.4.26 |
| 3 | 孤儿附件清理**两份实现**，且维护那侧把 GC 的 `due_at` 写成 `now + 30 天` | 对象在行删掉后**还要在 R2 里多躺 30 天** | v0.4.27 |
| 4 | `trashApi.restoreFolder` **零调用点**、回收站只查 `items` | 文件夹删掉后**在界面上消失且无法恢复**（内容只能逐条恢复到根目录） | v0.4.28 |
| 5 | **`itemsApi.getBody` 零调用点**：正文从不按需取，`load()` 只读本地库 | **新设备 / 清过本地库后打开笔记是空白编辑器**，一编辑就撞成冲突副本；而《同步引擎设计》§五 里这条（M1）还标着 ✅ | v0.4.31 |

### 8.2 两个审计手段（可复跑）

1. **调用点检查**：对每个"声称做完"的构件，在源码里找**非测试的调用点**。
   零调用点 = 未接线。还要顺带看"被引用了但从未被调用"的死导出（第 3 次那 4 个死函数就是这么发现的）。
2. **端到端可达性**：从 `apps/web/src/main.tsx` 出发，沿**静态 import 与动态 `import()`** 递归解析，
   得到"运行时真能加载到的模块集合"，再核验关键模块是否在其中。比"有引用方"更强——
   能抓出"被引用了、但那条分支永远不成立"。
   脚本是**只读的、放在仓库外**（不往仓库里塞工具文件），一次跑完 24 个候选模块。
3. **服务端端点覆盖**：把路由里声明的端点逐个拎出来，查测试目录里有没有真调用它的用例（本程：17/17 覆盖）。

### 8.3 本程审计结论

- 前端：**24/24 关键模块可达**（从 `main.tsx` 可达 135 个模块），四个 feature 下**无孤儿模块**；
- 服务端：**17/17 M4 端点有用例走过**；`routes/*` 全部挂载；
- **扩展审计（2026-09-27，覆盖 M1–M4）**：自动发现 `apps/web/src` 下**全部 144 个源码文件**逐个查可达性——
  **144/144 可达、0 个孤儿文件**；再对 82 个 `.tsx` 里导出的**大写标识符**（组件惯例）查"别处有没有当
  JSX / 工厂用"——只有 **4 个**只在**本文件**或**测试**里用（`COMPOSER_MODES` / `AUTO_LOCK_NOTICE_MS` /
  `EMPTY_SEARCH_STATE` / `TrashRetentionChip`），**没有"写了但从没渲染"的组件**。
  （`EMPTY_SEARCH_STATE` 是给测试用的导出；`TrashRetentionChip` 原本确实是死件，本轮已在回收站页头用上。）
- 同轮借审计发现并修掉一处**"接上了但接错"**：回收站页头把保留期写死成"30 天"、且 `useTrash` 算剩余天数
  时用的是默认值——**用户在设置里改成 7 天后，文案与倒计时都不跟着变**。现在保留天数从
  `user_settings.version_trash.trash_retention_days` 一路传到页头与剩余天数计算。
- **给后续里程碑的规矩**：声称某个前端构件做完时，必须能贴出它的调用点（grep 得到），
  否则一律记为未完成；收口前跑一遍 8.2 的三步。
