## 一、当前实现与线上部署关系

### 1. 已落地的代码批次

- **S1 服务端（v0.6.13）**：`shares` / `share_items` 迁移 0005；管理侧创建、列表、改密改期、撤销；公开侧状态、解锁、正文、附件；实时失效检查；无状态 HMAC 访问令牌。
- **S2 管理端（v0.6.14）**：笔记「更多 › 分享」入口、创建弹窗、设置 › 分享、公开标记、实例设置里的分享子域、加密 / 移入回收站后的分享行清理。
- **S3 查看器（v0.6.15）**：`/s/<分享ID>` 路径分流；失效页、密码页、只读 Markdown、附件令牌取回与 blob URL、只读表格网格、图册切换。

### 2. 入口实现的已知偏离

架构入口表原定 `apps/web/share.html` 独立入口；实际 `@cloudflare/vite-plugin` v1.60 接管客户端入口，手写第二 html input 会报 `UNRESOLVED_ENTRY`。现按架构同一节已经定下的 Static Assets SPA 规则实现：

- `/s/<分享ID>` 未命中静态文件时回落 `index.html`；
- `apps/web/src/main.tsx` 按 pathname 分流；
- 主应用与查看器均动态导入，分享访客不拉编辑器与同步 chunk；
- 偏离原因、回写目标已写在 `main.tsx` 与《M5 分享设计》v1.3 修改记录中。

这不是第二套页面骨架，也不拆 Worker；分享子域与主域仍指向同一个 Worker/Static Assets 部署。

## 二、Cloudflare 一次性部署动作

以下动作需要实例管理员在 Cloudflare 控制台或 DNS 提供商完成；代码仓库本身不应伪造这些外部状态。

1. 选定分享子域，例如 `share.example.com`。
2. 为该子域配置 DNS 记录，指向当前 Worker 的自定义域 / Workers 路由目标。
3. 配置 Workers Route：`share.example.com/*` → **与主应用相同的 Worker**。不创建第二个 Worker。
4. 在 Menote「设置 › 实例管理 › 分享子域」填入 `https://share.example.com` 并保存。留空时仍可用当前站点的 `/s/<分享ID>` 作为回退。
5. 确认 HTTPS 证书已对分享子域生效；分享查看器依赖 WebCrypto 的密码派生，HTTP 不作为线上验收环境。
6. 确认主应用会话 Cookie 仍不带 `Domain` 属性（当前 `middleware/session.ts` 的既有实现），使主域会话不会发到分享子域。

### 3. 点验查出的 P0：带密码的分享链接 100% 打不开（v0.6.18 已修）

**这是本轮点验最大的收获，也是「人工点验为什么不能省」的实证。**

用户按第 4 条输正确密码后仍打不开。查下来：unlock 请求**四次全部 HTTP 200**，界面却说「密码不对」——因为服务端的「密码错」也是用 200 返回的（`return { status: "wrong_password" }`），**看状态码与界面提示都拿不到线索**。

根因：`deriveSharePasswordMaterial()` **每次调用都生成一枚新盐**。创建者侧用它派生并把 `{kdf, salt, verifier}` 一起存库（正确）；**访客侧调的是同一个函数**，于是用另一枚盐派生，而服务端只做常量时间 HMAC 比对、**从不重新派生** → 两枚盐不同，PBKDF2 结果必然不同 → **任何密码都过不了**。

**契约本来就写对了**：`packages/shared/src/shares.ts` 的 `PublicShareStatus` 注释就是「设了密码才给：访客按它派生校验值」——服务端特意把 `salt` 与 `kdf.iterations` 发给访客；查看器**拿到了并存进 password stage，却从没传给派生函数**。所以不是设计缺陷，是实现没遵守自己定的契约。

**修复**（v0.6.18 `fc89345`，仅 `apps/web`，服务端零改动）：`features/shares/model.ts` 拆出 `deriveVerifier` 作 PBKDF2 唯一产地并新增 `deriveShareVerifierWithStoredParams`；`ShareViewerApp.submitPassword` 改用状态接口那组盐与迭代数，并对盐为空 / 迭代数为 0 显式报错。

**为什么自动化没抓到**：worker 用例直接注入 verifier、查看器用例 mock 了 unlock 响应，**没有任何一条用例真跑过两端派生往返**；原用例只断言「每次新盐 → 校验值不同」（创建者侧的正确行为），访客侧零覆盖。补 3 条往返回用例（web 4 → 7）。

### 4. 自动化与自动化都替代不了的

- **自动化替代不了**：真实 Cloudflare 子域路由、跨 origin 的会话隔离、浏览器真实 object URL 图片、表格密集内容视觉、真实 R2 附件请求、破坏性操作（撤销 / 移入回收站）。
- **本地已能替代的**：上面 §2 的十一项，不必再让用户重复点。
- **AI 侧点不了的**：`添加附件` 走系统文件选择器、任何密码输入框（安全守卫要求用户本人输入）。第 6 条后半与第 8 条因此只能由用户做。
- 自动化用例已覆盖的失效四路（撤销 / 过期 / 进回收站 / 被加密）见 `apps/worker/test/shares.test.ts`；S4 要点的是**界面观感与子域形态**，不是这套逻辑。

### 5. 环境备注（踩到的两件事）

- **`pnpm dev` 的后台任务上限 1 小时**（`exceeded maxRunMs`）。本轮 10:25 被运行时掐掉，之后「更多」菜单点不动——Worker 已经死了，**容易误判成前端 bug**，先看服务是否还活着。
- **浏览器面板宽度会变**：本轮中途从 1280px 被压到 **699px**，笔记工具栏的「更多」被裁到屏外，而该容器**不可横向滚动**，按坐标点击失效。窄屏下的工具栏溢出**目前没有兜底**（`DESIGN.md` §2.4 窄屏布局本就未定稿），登记在此，等移动端那批一并解决。
