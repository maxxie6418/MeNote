## 二、批 1：软删条目时连带撤销分享

### 2.1 根因

服务端 `isShareLive()`（`apps/worker/src/services/share-public.ts`）只做**实时检查**：`revoked_at` / `expires_at` / `item_deleted_at` / 加密标记。它**不记得这条分享曾经因为回收站死过一次**，所以条目一恢复、条件重新满足、链接就活了。

真正让需求成立的是**客户端那步**：`features/shares/model.ts` 的 `revokeItemShares()` 在删除条目时把分享行真撤销。两条现实路径会让它失效：

1. `revokeItemShares` 里每个 `revoke` 都被 `try/catch` 吞掉（注释写「留给实时失效兜底：链接反正已经打不开了」）——**但实时失效只是暂时**，撤销请求一失败，恢复后链接就回来；
2. **在另一台设备上**从回收站恢复条目，那台设备没有这条分享的上下文，客户端清理根本不会跑。

### 2.2 方案：服务端在软删时一并撤销

`softDeleteItem`（`apps/worker/src/services/trash.ts`）现在是两条语句的 `db.batch`，**加第三条**：

```sql
UPDATE shares SET revoked_at = ?
 WHERE item_id = ? AND user_id = ? AND revoked_at IS NULL
```

- **限定 `user_id`**：`shares` 有 `user_id` 列，直接限定即可（与 `attachment_refs` 那张无 `user_id` 的表不同，见批 2a）。
- **只在 `revoked_at IS NULL` 时写**：已撤销的不重复写。
- **不推进 `sync_seq`**：撤销是服务端行的状态变化，**所有设备共享同一份 `shares`**，下一次打开「我的分享」自然看到最新值；不像条目正文那样需要跨设备同步。
- **幂等**：已在回收站的条目，`softDeleteItem` 本来就早退（不进这条语句）；即使重复调用也不会二次推进。

### 2.3 与客户端那步的关系

**服务端成为正确性保证，客户端退化为「让用户知道」**：

| | 改前 | 改后 |
|---|---|---|
| 正确性 | 靠客户端 `revokeItemShares` | **服务端软删即撤销** |
| 提示「相关分享已自动撤销」 | 客户端触发 | 客户端保留（要拿到被撤销的条数来写提示） |
| 列表即时刷新 | 客户端触发 | 客户端保留 |

客户端**不改**：它照旧在删除后调 `revokeItemShares` 拿计数、发提示、刷列表；服务端已经撤过的行，`revoke` 会走「已撤销」分支、不重复写。

### 2.4 一个需要你拍板的边界：加密此篇要不要同样连带撤销？

需求 §16.1 只对**回收站**明写「不会自动恢复」。**开启单篇加密**同样会让链接实时失效，而**取消加密后链接也会复活**（同一套实时检查）——需求对此没写。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（本文推荐）** | 回收站 + 加密**都**连带撤销 | 比需求更严；「加密一下再解开」会让分享彻底死掉，可能不符合直觉 |
| B | 只做回收站（照需求字面） | 加密路径留同样的洞 |

**等你选**。选 A 的话 `patchItemMeta` 里 `enc_self` 置位那一步也要加同样的语句。

### 2.5 测试

- 软删 → 访客 `status:"invalid"`；**从回收站恢复 → 访客仍 `invalid`**（本批的核心断言）
- 撤销幂等：软删两次不报错、`revoked_at` 不被二次推进
- 跨租户：A 用户软删不影响 B 用户同名 `item_id`（用不存在的 `item_id` 验证语句不误伤）
- 撤销分享**不**影响附件、版本历史、条目本身
- 回归：分享的其余失效四路（撤销 / 过期 / 已删 / 已加密）行为不变

## 三、批 2a：保存正文时对齐引用集合

### 3.1 为什么必须**与正文同一次写**

引用表不准的后果不是「显示错」，而是**附件会被当孤儿删掉**：`SQL_MARK_ORPHANS_OF_USER` 判定「没有任何 `attachment_refs` 引用」就标 `orphaned_at`，满 30 天由每日维护删 R2 对象。若正文里明明还引用着某张图、引用表却已经没有它，**30 天后那篇笔记的图片就没了**。

所以对齐必须**原子**：与正文写在同一个 `db.batch` 里。分成两次请求（先存正文、再对齐引用）会留下一个「正文已存、对齐未成」的窗口，恰好是数据丢失的窗口。

### 3.2 契约变更（需你知晓）

`PUT /api/items/:id/body` 新增一个**可选**请求头：

| 头名 | 值 | 缺省行为 |
|---|---|---|
| `X-Menote-Refs` | `base64url(JSON.stringify(string[]))`——**sha256 列表** | **不传 = 完全不动 `attachment_refs`**（老客户端、批量路径的旧 op、第三方调用都安全） |

编码方式与既有的 `X-Menote-Meta` **同款**（`base64UrlEncodeUtf8(JSON.stringify(...))`，见 `packages/shared/src/items.ts` 的 `encodeItemWriteMeta`）。shared 里加一对 `encodeAttachmentRefs` / `decodeAttachmentRefs`，与 meta 那对放在一起。

**传 sha256 而不是 attachment_id**的理由：sha256 就是正文里出现的那个标识（`/api/attachments/h/<sha256>`），客户端本地能算出来；`attachment_id` 是服务端主键，客户端未必有（备份恢复出来的附件本地行可能不全）。服务端按 `sha256` + `user_id` 反查 `attachments.id`，**顺带把租户限定做掉**。

### 3.3 服务端两条语句（加进 `saveItemBody` 现有的 batch）

```sql
-- ① 清掉这条目「当前稿」的引用（version_id IS NULL 才是当前稿；历史版本的引用不动）
DELETE FROM attachment_refs
 WHERE item_id = ? AND version_id IS NULL

-- ② 按 sha 插入新引用；json_each 让整个数组只占**一个**绑定参数
INSERT OR IGNORE INTO attachment_refs (item_id, version_id, attachment_id, created_at)
SELECT ?, NULL, a.id, ? FROM attachments a
 WHERE a.user_id = ? AND a.sha256 IN (SELECT value FROM json_each(?))
```

- **为什么用 `json_each`**：一条 `INSERT` 逐行绑参会随图片数线性增长。D1 单条语句的绑定参数有上限（不是 SQLite 的限制），一篇带几十张图的笔记会顶爆。`json_each` 把整个数组压成**一个**参数。
  **⚠️ 待验证**：`json_each` 属 SQLite 的 JSON1 扩展，**D1 是否默认启用需在 worker 用例里实测**。若不可用，退路是**按 90 个一批分片**（同仓库别处已有分片的先例），代价是多几条语句。
- **传了 refs 但某个 sha 查不到对应附件**（例如备份恢复后服务端没有那行）：`IN` 天然跳过，**不报错**——宁可少一条引用（后续 30 天清理），也不要因为一条坏引用把整个保存打回。

### 3.4 批量路径必须一起改（否则离线推送时不对齐）

`POST /api/batch` 的 `save_body` 操作（`services/batch.ts` 复用同一个 `saveItemBody`）**也要能带 refs**——这是离线优先架构下的**主路径**，不是边角。若只改直接保存，离线重连后推的一批保存会全部不对齐引用。

所以 batch 的 op 形状要加一个可选 `refs`。**这里同样有绑定参数预算问题**：`BATCH_MAX_OPS` 是 10，一个 op 内的 refs 用**同一个 `json_each` 技巧**压成一个参数，不额外顶预算。

### 3.5 客户端

- 保存正文时从正文里抽引用。**函数已经有了**：`packages/shared/src/attachments.ts` 的 `extractAttachmentRefs(body)`——分享查看器取附件用的就是它（`features/share-viewer/model.ts` 的 `loadAttachmentBlobs`）。**不另写一套解析。**
- 直接保存与 outbox 批量两条路径都要带上（前者直接加请求头，后者塞进 op）。
- 落点：`data/api/endpoints.ts` 的 `saveBody` + `data/sync/push.ts` 的 `save_body` op 组装。

### 3.6 测试

- 带 refs 保存 → `GET /api/attachments/refs/:itemId` 返回新集合
- 不带 refs 保存 → 引用集合**原样不动**（向后兼容的硬断言）
- refs 里混入不存在的 sha → **不报错**、其余正常写入
- 带 `version_id` 非 NULL 的历史版本引用**不被清掉**
- 跨租户：B 用户的 sha 传进 A 的条目 → 不写入
- 正文删掉一张图后保存 → 该图引用消失、其余保留（**这正是本批要修的行为**）
- 原子性：正文写入与引用对齐在同一次 batch，中间无窗口

## 四、批 2b / 2c：删除引用入口与附件管理页

### 4.1 删除附件引用入口（M10-新）——**入口取舍待你确认**

功能拆解 M10-新 给了三个候选（附件旁图标按钮 / 选中后常驻小工具条 / 收进更多菜单），文档里的**默认取舍**是「**更多菜单为主 + 选中后常驻小工具条为辅**」（同一动作两个入口，**都不靠悬停**）。本文沿用这个默认，但**它标着「待拍板」，请你点头或改**。

- 动作语义必须写清（原文照搬）：**移除引用 ≠ 删除文件**——「只从这篇的附件章节移除引用；文件本身在没有别处引用满 30 天后才会被清理」。
- 不提供「删除附件文件」入口——那属附件管理页（4.2）。
- 实现上是删掉正文里 `![名](/api/attachments/h/<sha>)` 这一段。本地那条没人调用的 `removeAttachmentMeta`（`data/db/attachments.ts`）正好在这里接线。

### 4.2 附件管理页（M10-03）：块与主操作

入口：**设置 › 数据管理 › 附件管理**。**注意「数据管理」这个分类当前不存在**——设置导航现有 9 类，「数据管理」与「MCP」都还没进（功能拆解 M18-01 记着这两个属 M6）。本批要**新建「数据管理」分类**。

| 块 | 内容 |
|---|---|
| 概览 | 附件总数、**占用空间**（M4 设计 §十-4：附件不设硬配额，占用只在这里显示）、孤儿数 |
| 列表 | 每行：缩略图（无缩略图回退文件图标）、文件名、类型、尺寸、**被多少条目引用**、状态（在用 / 孤儿） |
| 主操作 | **手动清理孤儿附件**（二次确认，**写明后果**：不可撤销、占用的空间会真正释放） |
| 空状态 | 三种分清：①一个附件都没有（「正文里插入图片会自动上传到这里」）；②有附件但**没有孤儿**（「当前没有可清理的孤儿附件」）；③筛选后为空 |

视觉全部走 `DESIGN.md`（`setrow` 行式布局、按钮层级、表格列宽），**不新造组件**。附件管理页是**新屏**，按「先稿后码」：实现前先把这一屏的块与空态在本文定稿、你确认后再写界面代码。

### 4.3 一个 M4 留下的缺口：列表接口不存在

功能拆解 M10-03 要求「列出所有附件、占用空间、孤儿附件」，但 `apps/worker/src/routes/attachments.ts` 现有接口只有：`check` / `blob` / `finalize` / `h` / `refs/:itemId` / `gc`。**没有「列出本用户全部附件」的接口。**

本批需新增（会话鉴权，只列本用户）：

| 接口 | 用途 |
|---|---|
| `GET /api/attachments?kind=original\|thumb&state=active\|orphaned` | 列表：id、sha256、文件名、mime、尺寸、字节数、`orphaned_at`、引用它的条目数 |
| — 占用空间 | 由列表在客户端求和即可，**不单独设接口**（少一个端点、少一份契约） |

排序按 `updated_at` 倒序；分页先不做（个人自用规模），但**接口要留 `limit`/`cursor` 位**，免得以后改契约。
