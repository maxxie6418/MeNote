## 一、这次校准的口径

用户 2026-10-03 拍板：**不等实测，按估计值定参数**。于是本篇遵守三条：

1. **每个数字都标来源**：【实测】有本次量出来的数；【估计】有依据但没量；【未知】既没量也不知道量级。**不把估计写成实测**——预算表里混进一个没量过的数，三个月后就没人分得清它是量出来的还是拍的。
2. **实测项优先用真数据**：M1–M6 期间零散量过的数（首屏包体、512 KB 小节解析、测试规模）直接收进 §十四，不重造。
3. **留「重算条件」**：每个估计值写明"什么情况下它不再成立"。没有重算条件的预算等于没有预算。

## 三、Worker CPU 预算（架构 §14.2）

| 接口 | 估计 | 现状 | 来源与依据 |
|---|---|---|---|
| 会话鉴权 | < 0.5 ms | 维持 | 1 次 SHA-256 + 1 次 D1 读，与 CPU 预算量级无关 |
| 增量拉取（200 行） | 1–2 ms | 维持 | JSON 序列化；每页 200 行上限是硬防护 |
| 读取 / 全文保存 2 MB 正文 | 数毫秒 | 维持 | 原文走请求体不用 JSON；1102 时客户端改用补丁 |
| 补丁保存 | < 1 ms | 维持 | 几 KB JSON，最多 20 个操作 |
| 附件与版本上传下载 | < 1 ms | 维持 | 流式转发不缓冲请求体 |
| MCP 区间读取、搜索片段 | < 2 ms | 维持 | SQL 截取，条数与字符数双上限 |
| **MCP 小节解析（≤ 512 KB）** | ~~待实测~~ | **解析 + 整条 HTTP 往返 20 ms**（390,040 字节中文正文） | 【实测】`apps/worker/test/mcp-read.test.tsx` 那条用例，**在 workerd（`@cloudflare/vitest-pool-workers`）里跑**。**更强的一条信号**：该请求**没有触发 10 ms CPU 限额**——若超了，workerd 会直接抛错。**门槛因此维持 512 KB 不下调**（定稿 §十七-4 已同步） |
| 服务端版本压缩（≤ 256 KB） | 待实测 | 【未知】`CompressionStream` gzip，未量 | 重算条件：条目封存变慢、或 R2 写入报超时 |
| **Cron 备份出站加密（≤ 4 MB/轮）** | ≈ 2–4 ms | 【估计】AES-GCM（WebCrypto），**未量** | 用户拍板不等实测。**这个数直接决定单轮加密配额**，所以定参数时按 4 ms 打满算（即先按 2 MB/轮 而不是 4 MB/轮 留余量）——见 §四 |
| Cron 每轮 | 多个小任务 | 由配额控制 | 见 §四，那里有条**不自洽**要改 |

**关于 20 ms 那个数该怎么读**：它是**墙钟**（含 D1 往返 + 序列化），不是纯 CPU。纯 CPU 只会更小。所以"没触发 10 ms 限额"是比"20 ms"更硬的结论——但**生产的 CPU 计量口径仍应以 Workers 日志为准**（miniflare 的限额实现与生产是否逐项一致，官方未承诺）。所以定稿里写的是"门槛不动"，而不是"CPU 只需 X ms"。

## 四、子请求上限：一条必须记住的硬数字【本篇最重要的一节】

**Cloudflare 官方限额（2026-02-11 changelog + Limits 页）**：

| 类别 | 免费版 | 付费版 |
|---|---|---|
| **外部** 子请求（`fetch()` 到互联网：WebDAV / S3 / 第三方 API） | **50 / invocation** | 默认 10,000，可用 `wrangler.jsonc` 的 `limits.subrequests` 调到 1000 万 |
| **Cloudflare 内部服务**（R2 / D1 / KV / DO 绑定） | **1000 / invocation** | 1000 / invocation（**与套餐无关**） |

**这条把《定时自动备份设计》§二 的单批参数否掉了。** 那份设计写「一轮 Cron 内每目标最多推 20 批 / 批 40 文件」＝ **一次 invocation 推 800 个文件**。但 WebDAV / S3 走的是 `fetch()`，属**外部**——**免费版一次 invocation 最多 50 个，800 不可能**。而且设计上「Cron 触发每日一次」，等于**每天只能推约 45 个文件**（留 5 个余量给健康检查等）；一个 500 文件的库首轮全量要 **11 天**。

**这不是"参数待定"，是设计里的一处不自洽**，三处口径必须先改：

| # | 现状 | 问题 | 建议 |
|---|---|---|---|
| 1 | Cron「每日一次」 | 每天只 45 个外部 PUT | **改为按配额推**：复用 `wrangler.jsonc` 已有的 `*/15` 触发器，备份任务每轮推一批（每轮 ≤45 外部 PUT），游标续推。每天 96 轮 × 45 ≈ 4300 文件/天，500 文件的库**两轮就完**。设计稿 §二 的"每日一次"与它自己写的"复用已有 `triggers.crons`"本来就矛盾 |
| 2 | 「批 40 文件」 | 40 是**外部 PUT** 的数，一次 invocation 最多 ~45，所以**一批就顶满**，"20 批"只能跨轮 | 改成「**每轮一批，批内 ≤40 外部 PUT**」，批数由每 15 分钟的轮次自然给出 |
| 3 | 「每轮加密 ≤ 4 MB」 | 出站加密是纯 CPU（AES-GCM），不含子请求；2–4 ms 是**估计值**未量 | 定参数时按 **2 MB/轮**起步（4 ms 的下界），量过之后再放宽。**这条与子请求无关**，两条余量分别留给 CPU 和外部 PUT |

**顺带一条部署建议**（可配，不做也能跑）：在 `wrangler.jsonc` 显式写死上限做兜底，让"写飞了"变成响亮失败而不是额度告警：

```jsonc
"limits": { "subrequests": 50, "cpu_ms": 1000 }
```

不写的后果是撞上平台默认 50 / 1000 ms 时报错信息更难读。**这是可选加固，不是本轮要改的**——改它属于部署配置变更，按 AGENTS.md 要先问。

## 五、留待实测的清单

按"最该先量"排序。用户 2026-10-03 拍板不等实测，所以这四条**留在台面上**，触发条件写在最后一列：

| 待测项 | 怎么测 | 触发重算的条件 |
|---|---|---|
| 2 MB 文档连续输入 | 真机 + Performance trace | 家人反馈"打字会顿" |
| 冷启动 1.5 秒 | 中端安卓机，冷启动计时 | 低端机反馈打开慢 |
| 出站加密 2–4 ms | 生产压测读 Workers 日志的 CPU 时间 | 备份轮次频繁超时 |
| 服务端版本压缩 | 同上 | 封存变慢 |

**什么时候该回来做实测**：①部署实例的真实数据量超过预估；②上付费版（外部子请求从 50 跳到 10,000，备份的整套参数要重算）；③真机反馈性能问题。
