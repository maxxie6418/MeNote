## 一、已确认的产品结论

### 1. 内容输入不是一套“模式”，而是按场景分层

MeNote 有两类文本输入场景：

| 场景 | 用户目标 | 产品重点 |
|---|---|---|
| 快捷输入 | 快速记录一条 Memo、待办或笔记草稿，并立刻看清重点与列表结构 | 轻量、所见即所得、多个输入框同时存在也稳定 |
| 笔记正文 | 持续写作、编辑长文、阅读和检查最终排版 | 内容可靠、长文性能、最终以即时渲染编辑为主 |

两者应当让用户感觉是同一种 Markdown 内容体验，但**不要求使用同一个编辑器内核**。共享的是 Markdown 语义、基础格式命令、命令名称和正文主题语义；实现可以按短内容和长内容的性能需求拆分。

### 2. 正文不再保留四档，明确移除双栏

原有“编辑 / 预览 / 即时渲染 / 双栏”四档不作为最终产品形态。双栏需要同时维持编辑与渲染区域、增加长文渲染和滚动协同负担，但不是最终主要写作体验，明确不保留。

**实施结果（2026-09-29，阶段 A–C）**：正文生产模式为三档——**仅编辑 / 仅预览 / 即时渲染**；双栏从产品移除（`EditorModeSchema` / `EDITOR_MODES` 仍读得进旧值，UI 与新写入只产生三档）。「打开笔记看见哪一档」由本机记住的“上次用的那一档”决定，设置里的 `editor_mode` 只是首次初始值。

正文最终有三种呈现状态：

| 状态 | 是否可编辑 | 产品角色 |
|---|---:|---|
| Markdown 编辑 | 是 | 可靠的源码编辑、兼容与兜底入口；也服务熟悉 Markdown 的用户。 |
| 即时渲染编辑 | 是 | **最终默认与重点打磨的写作形态**：尽量按最终排版显示，用户可直接持续输入。 |
| 预览 / 阅读 | 否 | 稳定、没有编辑干扰的完整阅读与检查状态。 |

“即时渲染只读”不在首期作为新的用户可选档位。它是即时渲染的不可编辑形态，可在内容被锁定、无编辑权限或业务需要只读时复用；**2026-09-29 已拍板：由“预览”统一承担阅读态，不再保留独立的锁定呈现入口**（`Editor` 的 `readOnly` 只作内部能力）。

### 3. 快捷输入默认采用轻量即时渲染

快捷输入不应只是纯文本框。Memo、待办、笔记快捷录入和添加内容窗口中的短内容，默认应能直接显示基础 Markdown 的效果，不需要用户另切预览。

其目标是“快速记下，并马上看清结构”，而不是承载完整长文编辑器。快捷输入的即时渲染不要求与正文采用同等复杂的逐字符内联编辑方式，但**呈现时机是硬要求**：**【v3.3 收紧·用户 2026-09-30 反馈后定】**用户打字过程中，**已完成的块必须即时按 Markdown 呈现**（写一行、回车、上一行当场呈现），光标所在的当前块保持 Markdown 源码。**【v3.4 定·用户 2026-09-30 拍板】**`/` 命令的结果**在提交该块之后**当场呈现（回车、或点到别的块）——**不要求"应用瞬间就呈现"**：当前块按本条要求保持源码，而命令插入的是成对标记（如 `****`）或行前缀（如 `- `），要让"应用即呈现"就必须把光标挪出这一块（多一个空块或暂时失焦），代价由用户的打字流承担，不划算。**“失焦整块呈现”只能作为兜底，不算满足本目标**——阶段 B 的实现只做了失焦这一个时机（`QuickComposer` 的 `showView = !editing && …`），用户 2026-09-30 验收时当即发现"换行不呈现、`/` 后看不到效果"，本条原文里"完成当前块、失焦**或**查看时"那个"或"字就是漏洞来源：它让最省事的一种时机也算过关。实现方式仍由实施计划定（现行口径见 `docs/todo/Menote-快捷输入块级即时渲染-实施计划-v1.md`），但不得因为渲染而打断中文输入、列表连续输入或焦点。

### 4. 表格沿用“编辑 / 锁定浏览”的共同原则

表格编辑 / 锁定浏览属于后续产品方向，不限定在当前阶段实施计划中；启动时另立专项设计。

笔记与表格共享一条产品原则：内容对象始终区分可编辑与不可编辑状态。

- 笔记：Markdown 编辑、即时渲染编辑属于编辑；预览 / 阅读和即时渲染锁定属于不可编辑。
- 表格：网格编辑属于编辑；网格浏览 / 锁定属于不可编辑。

表格是结构化内容，不强行套用 Markdown 的预览模式或即时渲染交互；只复用“编辑 / 锁定”的上层原则。

## 二、分阶段产品路线

### 阶段 A：先稳定投入使用的正文基础

首个可投入使用的正文版本只提供：

```text
Markdown 编辑  ↔  预览 / 阅读
```

目标是先保证：

- 可以稳定编辑和保存 Markdown；
- 可以稳定查看最终排版；
- 切换文章、编辑与预览不明显卡顿；
- 预览与编辑保存的是同一份内容；
- 不为即时渲染的视觉细节阻塞基础可用性。

本阶段不保留双栏，不要求即时渲染上线，也不以视觉精修为验收前提。

### 阶段 B：先在快捷输入打磨轻量即时渲染

快捷输入优先验证并交付轻量即时渲染。原因是内容短、用户更在意即时显示效果，且不涉及长文滚动与复杂文档状态，适合作为最终编辑体验的低风险试验场。

本阶段重点是：

- 基础格式在输入后可直接看出效果；
- 多个快捷输入框并存时仍然流畅；
- 输入法、连续列表、撤销和焦点不受破坏；
- 快速发布的路径不被编辑效果拖慢；
- 保存内容仍是 Markdown，而不是新增第二种文档格式。

### 阶段 C：重点打磨正文即时渲染编辑

在正文的 Markdown 编辑和预览已稳定、快捷输入的基础经验已验证后，再交付：

```text
Markdown 编辑  ↔  即时渲染编辑  ↔  预览 / 阅读
```

即时渲染达到稳定标准后，成为新笔记的默认编辑形态；Markdown 编辑仍保留为兼容、兜底和高级编辑入口，不能因为即时渲染尚未覆盖复杂内容而被删除。

即时渲染的首要验收不是视觉“像不像成品”，而是：中文输入不丢字、光标和选区稳定、列表与代码等结构连续输入正常、撤销/重做可靠、长文不因反复操作越来越慢、保存后重新打开的内容一致。

## 三、格式能力的产品边界

### 1. Markdown 是唯一持久化内容格式

快捷输入、正文 Markdown 编辑、即时渲染编辑和预览都围绕同一份 Markdown 内容工作。

即时渲染是输入与显示方式，不是第二种文档格式。用户直接键入 Markdown 的习惯继续有效；`/` 命令只是生成或转换同一份 Markdown 的快捷入口。

### 2. `/` 样式快捷：两处都有，能力分级

`/` 只处理内容样式或结构，不处理条目的业务属性。它同时适用于快捷输入和正文，但不要求两个场景的命令数完全一样。

| 命令集合 | 快捷输入 | 正文 |
|---|---:|---:|
| 加粗、斜体 | 是 | 是 |
| 无序列表、有序列表 | 是 | 是 |
| 引用 | 是 | 是 |
| 行内代码 | 是 | 是 |
| 链接 | 是 | 是 |
| 标题 | 否 | 是 |
| 代码块 | 暂不作为首期要求 | 是 |
| 任务清单 | 按 Memo / 待办场景需要提供 | 是 |
| 图片 / 附件插入 | 否 | 是 |

快捷输入只承担高频、易理解的基础集合；正文承担完整写作能力。两处的同名命令应输出同一种 Markdown 语义，视觉名称和图标也保持一致。

**实施结果（2026-09-30，v0.6.3）**：快捷输入的基础集落地为**加粗 / 斜体 / 无序 / 有序 / 引用 / 行内代码 / 链接**（表里"是"的那几行），标题"否"、代码块"暂不作为首期要求"均不提供；**任务清单按表里那句"按 Memo / 待办场景需要提供"实现**——`quickFormatCommandsFor(host)` 给 Memo 与待办追加 `task-list`（与正文同一个 id、同一种语义 `- [ ] `、同一个名称"任务清单"），笔记快捷录入首期不给。`/图片`、`/附件`（表里正文＝是、快捷输入＝否）仍未接入正文，登记在 `docs/todo/Menote-开发计划-v1.md` 的「遗留 → 后续」表。

图片 / 附件插入属于正文宿主的异步内容动作，不等同于加粗、列表、引用等同步 Markdown 格式命令。它的产品目标是让用户能在正文中便捷插入图片或附件，并看到可靠的内容引用；具体上传、占位、替换和失败处理由实施方案决定。

### 3. `@` 属性快捷：只用于快捷输入

`@` 的产品目标不是编辑正文文本，而是在“创建一条内容”时快速补齐属性。它只出现在快捷输入与添加内容窗口，不进入笔记正文。

| 快捷输入类型 | `@` 可处理的属性 |
|---|---|
| Memo | 标签 |
| 待办 | 优先级、日期等任务属性 |
| 笔记快捷录入 | 发布目标 / 文件夹等创建属性 |

这些属性属于快捷输入的产品能力目标：用户可以在输入内容的过程中补齐该类型内容的关键属性，并在发布时得到预期结果。具体属性如何暂存、选择和写入，由各阶段实施计划决定，不改变本节的产品目标。

正文中的标签、文件夹、日期等属性，仍通过标题区、属性面板或更多菜单等显式入口修改。这样避免用户混淆“正在改正文”与“正在修改整篇内容的属性”，也避免将领域操作提前塞进正文即时渲染的复杂交互中。

### 4. 明确排除下划线与任意样式

下划线不属于本轮能力范围。它不是基础 Markdown 语法，不为它引入 HTML 或私有格式扩展。

同样不做：任意字体、字号、任意颜色值、用户 CSS，或为了显示效果产生第二套内容格式。

## 四、体验一致性与性能取舍

### 一致性应来自语义，而不是强制同一实现

快捷输入和正文应当保持：

- 相同 Markdown 内容在保存后具有相同语义；
- 相同基础 `/` 命令产生相同结果；
- 相同标题、加粗、列表、引用、链接、代码等语义使用同一套主题语言；
- 用户可直接输入 Markdown，不被命令菜单取代；
- 输入、预览和锁定阅读不会互相篡改内容。

但它们不必保持：

- 相同编辑器引擎；
- 相同命令总数；
- 相同的实例数量和生命周期；
- 相同的即时渲染范围。

### 性能优先级

1. 任何场景都不能因反复切换、聚焦或输入而越来越慢。
2. 快捷输入优先保证多个实例并存与快速响应。
3. 正文优先保证长文输入、切文章和模式切换稳定。
4. 即时渲染若影响可靠输入，则可靠输入优先；用户始终可回退到 Markdown 编辑。
5. 预览和锁定阅读应尽量复用同一套阅读呈现，避免维护两套不一致的排版。

## 五、试验与生产替换边界

设置中的“编辑试验”页继续作为验证空间：样文和输入只在本机试验存储中存在，不写入正式笔记库、不上传、不同步、不进入搜索。

试验的目的依次是：

1. 验证正文“Markdown 编辑 + 预览”的基础稳定性；
2. 验证快捷输入的轻量即时渲染与基础 `/`、`@`；
3. 验证正文即时渲染是否可以在不牺牲可靠输入的前提下成立；
4. 再决定各生产场景的替换顺序。

未通过稳定性验证前，不替换正在使用的生产编辑器。生产替换仍以低风险场景开始：快捷输入与添加内容窗口先于 Memo 原位编辑，笔记正文最后替换。

## 六、明确不做

- 不保留正文双栏模式。
- 不把即时渲染尚未验证的版本直接替换生产正文编辑器。
- 不要求快捷输入与正文复用同一编辑器内核。
- 不在正文中首期加入 `@` 属性菜单。
- 不给搜索框、笔记标题或表格单元格加入本轮 `@` / `/`。
- 不支持下划线、任意 CSS、任意颜色值或第二套文档格式。
- 不把表格改造成 Markdown 即时渲染编辑器。
