## 一、术语与前提

### 1.1 术语

| 术语 | 含义 | **不是什么** |
|---|---|---|
| 加密空间 | `folders` 表中 `is_enc_space = 1` 的内置行：每账户一条、depth = 0、不可删除、不能建第二个【定稿 M08-07】 | 不是密码学加密。名字里的"加密"只是文案，它与单篇加密不属同一类机制【已定·用户确认】 |
| 隐私范围（scope） | 隐私锁**一次解锁**所覆盖的内容集合：默认含加密空间，可配置含 Memo 及其衍生的待办，预留后续扩展位 | 不是"另一个容器"，它是一份**类别清单**，决定门禁覆盖谁 |
| 隐私锁 | **范围门禁** ＋ **备份出站加密**，两者共用同一把隐私密码 | 不加密存储中的内容（见 P1） |
| 单篇加密 | `items.enc_self = 1` 条目的**独立门禁**，逐篇解密 | 不属于隐私范围；不受隐私锁解锁影响【已定·用户确认】 |
| 隐私内容 | 加密空间内条目（`in_enc_space = 1`）＋ 在范围内的 Memo 与待办 ＋ 单篇加密条目（`enc_self = 1`） | — |
| 范围解锁 | 输入隐私密码后，范围内全部内容对界面可见 | 不解开任何单篇加密条目 |
| 逐篇解密 | 对单篇加密条目单独输入隐私密码，**仅该篇**在本次会话内可读 | 不是"解开隐私锁顺带解开" |
| 会话态 | 只存在于浏览器内存、**不落库、不同步**的门禁状态：隐私锁解锁态、单篇已解密集合、档位计时器 | 不是一条数据，换设备/换标签页重来 |

### 1.2 三条前提

**P1 内容明文存储【已定·用户确认 2026-09-26】**：D1 与本机 IndexedDB 中，正文、标题、文件夹名、附件**都是明文**；隐私只是 `items.enc_self` / `items.in_enc_space` / `folders.is_enc_space` / `folders.in_enc_space` 这几个元数据标记。因此锁定只影响**前端渲染与检索可见性**，不影响存储，也不产生任何加解密动作。

**P2 隐私密码只有两个用途**【定稿 M08-09 技术说明】：① 前端门禁校验（本地 verifier）；② 备份出站加密（内容密钥 K）。服务端**不参与**密码校验。

**P3 保护边界如实告知**【定稿 M08-01】：启用时与确认框里都必须写清边界——不防已登录账号、不防服务端与本机缓存/日志、不防对备份文件的离线爆破。已接受的元数据泄露：条目数量、大小、时间、置顶与收藏、附件数、层级（定稿 v7.4 §6.5）。

### 1.3 保护边界（实现与文案共用同一口径）

| 能防 | 不能防 |
|---|---|
| 身边的人偷看屏幕：锁定时范围内内容整体占位或从列表消失，搜索、Memo、待办、筛选结果一并处理 | 知道你**登录密码**的人（登录后可直接调接口拿明文） |
| 第三方备份里直接翻到私密内容：隐私条目出站前强制加密 | 服务器管理员、拿到 D1/R2 备份的人 |
| 误分享、误让 AI 读到：MCP 与分享对隐私内容一律不可见（见第五章） | 本机浏览器缓存被翻（IndexedDB 里是明文） |
| 爆破者的时间成本：PBKDF2-SHA-256 600k（KDF 与参数见待写的第三～四章） | 专业者绕过备份文件的密码 |

## 二、三种机制对照

### 2.1 对照表

| | 机制一：隐私锁（范围门禁） | 机制二：单篇加密（独立门禁） | 机制三：MCP 可见性（独立配置） |
|---|---|---|---|
| 保护对象 | 隐私范围（加密空间 + 可配置的 Memo/待办 + 扩展位） | 单篇笔记/表格（`enc_self = 1`），留在原位、标题明文 | 不是锁：各内容类别对 MCP 的可读性 |
| 入口 | 顶栏胶囊、解锁框、点范围内的内容 | 编辑器「更多」菜单、条目上的锁标识 | 设置 › MCP 的令牌配置 |
| 解锁方式 | 一次输隐私密码 → 范围内**全部**可见 | **逐篇**输隐私密码，每篇状态独立【已定·用户确认】 | 不涉及解锁；由令牌配置决定 |
| 时效 | 三档：本次会话（多标签共享，全部标签关闭即锁）/ N 分钟无操作（默认 5）/ 当前设备长期（手动锁）【已定·用户确认】 | **本次浏览器会话**；可手动锁上（本篇 / 全部单篇）【已定·用户确认】 | 与隐私锁状态**无关**，不随范围设置变化 |
| 与对方的关系 | — | **不受隐私锁解锁影响**；隐私锁全开时它照样锁着 | 与隐私范围**解耦**：Memo 在范围内也不等于 AI 不能读（反之亦然） |
| 锁定/未解密时表现 | 空间不可展开、范围内容占位或消失，不进列表、搜索与筛选结果 | 明文标题 + 锁标识；**标题可搜**，正文不渲染也不进搜索 | — |
| 解锁/已解密后的额外效果 | 空间内条目**进入最近编辑、收藏、标签**（解锁期间可见，重锁即隐藏）；正文可搜 | 标题与正文都可搜 | — |
| 计数 | **统计计数一律计入**（空间节点、文件夹树、首页、标签云…），不因锁定改变【已定·用户确认】 | 计入统计计数 | **不计入**：MCP 侧的条目数与空间节点都不含隐私内容（见 5.3） |
| 备份出站 | 范围内内容强制加密 | 同样强制加密 | — |

### 2.2 三条不变式

1. **三者互不替代**：解锁隐私锁 ≠ 解开单篇；把 Memo 加入范围 ≠ 禁止 AI 读 Memo；任何一种都不能推出另一种。
2. **可以叠加**：空间内条目若同时带 `enc_self = 1`，则先进隐私锁（可见其位置与标题）、再进单篇门（才能读正文）。
3. **只有两个维度会改动"谁能看见什么"**：界面门禁（范围 × 隐私锁状态）与 MCP 令牌配置。两张矩阵**互不联动**（见 5.3）。

## 三、隐私范围与配置

### 3.1 成员与默认值

| 成员 | 默认 | 可否配置 | 判定来源 |
|---|---|---|---|
| 加密空间（含其内部文件夹与条目） | **在范围内** | 不可移出——它是范围的本体【本文决定】 | `folders.is_enc_space = 1` / `items.in_enc_space = 1` |
| Memo | **在范围内** | 可开可关 | 账户级设置项 `privacy.scope.memo` |
| 由 Memo 衍生的待办（清单视图 / 看板） | 跟随 Memo 开关 | 同 Memo，**一个开关管两者**【本文决定】 | 同上 |
| 后续内容类型 | 不在范围内 | 逐个加入 | 扩展位（见 3.4） |

> Memo 默认在范围内，与既有定稿 M08-16 的"Memo 浏览需要隐私密码（默认开）"一致；该设置项在 M3 里改为范围配置的一部分，文案与落点见待写的第七章。

### 3.2 范围变化的语义

- 加入范围 / 移出范围**都是元数据操作**，不涉及任何加解密，锁定态下同样可执行。
- **移出范围立即恢复普通可见**：Memo 移出后锁定时照常显示；空间内的条目不能单独移出范围（它们由空间归属决定，移出＝移出空间，那是另一条规则 M08-10）。
- 范围变化**不影响**已存在的单篇加密标记——那是机制二，有自己的开关。
- 范围变化不产生版本、不进回收站、对 MCP 可见性**无影响**。

### 3.3 配置项与落点

| 配置项 | 落点 | 值 |
|---|---|---|
| 范围成员 | `user_settings` 的 `privacy.scope` | `memo: boolean`（space 恒真，不落库或恒为 true） |
| 默认档位 | 同上 | `tier: 'session' \| 'minutes' \| 'device'` |
| N 分钟时长 | 同上 | 1 / 5 / 15 / 30 / 60，默认 5 |
| 解锁时可搜索加密内容 | 同上 | `unlockSearch: boolean`（作用范围见 5.1） |

设置随 `user_settings` 整份同步（M2 已有通道，不参与游标）；`privacy.scope` 写成"内容类别 → 布尔"的映射，**新增类别只加一项，不改门禁判定签名**（签名见待写的第三章）。

### 3.4 后续扩展位的约束

新内容类别加入范围时必须满足两条：① 它是**可枚举的内容类别**（不是单条数据）；② 它的"锁定表现"能在界面上明确表达（占位、隐藏或收起三选一）。不满足就不进范围——否则门禁会出现"半遮半掩"的状态。

## 四、锁定与解锁：状态、时效、触发

### 4.1 状态集合

| 机制 | 状态 | 说明 |
|---|---|---|
| 隐私锁 | 未启用 / 已锁定 / 已解锁 | 未启用时不存在单篇加密（前置：已启用【本文决定】） |
| 单篇加密（逐篇） | 未加密 / 已加密·未解密 / 已加密·已解密（本次会话） | 与隐私锁状态**正交**：解锁隐私锁不解开它，锁定隐私锁也不清它的已解密集合 |

### 4.2 三档时效【已定·用户确认 2026-09-26】

| 档位 | 覆盖 | 重锁触发 |
|---|---|---|
| 本次会话 | 隐私范围全部 | 所有 Menote 标签页关闭（多标签共享同一解锁态） |
| N 分钟 | 隐私范围全部 | 无操作 N 分钟后（N 默认 5） |
| 当前设备长期 | 隐私范围全部 | 手动"锁定此设备"（选择时须勾选风险确认） |

**已作废**：原"仅本次查看"档（本会话内只放当前一篇/一个空间）与"标签页隐藏即锁"——两者在 2026-09-26 的修订中先后被合并/取消【已定·用户确认】。定稿 M08-04 的四档表与 M08-05（Q14）随之改写，见附录 B。

### 4.3 触发清单

**解锁**：点顶栏胶囊 / 打开范围内的内容 / 在 Memo 或待办视图点"解锁" / 打开单篇加密条目（进的是**单篇**解锁框）。

**锁定**：
- 顶栏胶囊「立即锁定」——默认**锁全部**：清隐私范围解锁态 ＋ 清单篇已解密集合【本文决定；理由：点"立即锁定"的心理预期是"立刻都别看了"】；
- 档位到期（N 分钟无操作 / 最后一个标签页关闭）；
- 「锁定此设备」（设备长期档）；
- 登出（沿用认证设计：登出即锁定）。

### 4.4 锁定时做与不做

**做**：
1. 未保存的改动按**普通保存流程**先入库（不涉及加解密）；
2. 加密空间收起、范围内内容切占位或从列表移除；
3. 搜索与筛选结果中的隐私内容、Memo 立即消失；
4. 状态标识切到锁定态；剩余 30 秒时胶囊闪烁一次并提示（文案见待写的第九章）。

**不做**：
1. 不做任何加解密、不重写内容、不产生版本；
2. **不清本地缓存**（明文仍在 IndexedDB，符合 P1/P3，文案不得暗示"数据已保护"）；
3. 不改动数据的 `rev` / `sync_seq`（锁定是纯前端状态）。

### 4.5 单篇的逐篇解密

- **逐篇**：每篇独立状态，互不联动【已定·用户确认】。解开 A 篇不会让 B 篇可读。
- **时效**：本次浏览器会话；关闭标签页自然失效。
- **多标签共享**：会话内在同源标签页之间共享【本文决定，与隐私锁会话档一致】，走现有 `BroadcastChannel` 通道，不落库、不同步。
- **手动锁上**：编辑器/锁标识上的「锁上此篇」；顶栏「立即锁定」的"锁全部"；另有"锁上全部单篇"入口。
- **密码**：复用同一把隐私密码；"逐篇"指**门禁状态独立**，不是每篇一个密码【本文决定】。若将来要"不启用隐私锁也能单篇加密"，需要独立口令与 per-item verifier，属另一套设计。
- **不改数据**：解密只是门禁状态，正文、标题、附件都不重写。

### 4.6 离线

- 解锁与锁定**可离线**：verifier 有本地缓存时校验全在浏览器完成【定稿 M08-03】。
- 启用 / 修改 / 重置 / 关闭隐私锁**需联网**（要写服务端）。
- 本地 verifier 缓存是否随登出清除，取决于 Q22（登出是否清除本机缓存）——**Q22 未决，M3 开工前必须定**【待确认】。

### 4.7 计数口径【已定·用户确认 2026-09-26】

| 计数种类 | 举例 | 口径 |
|---|---|---|
| **统计计数** | 首页统计卡片、导航节点、文件夹树、标签云数字等一切"某集合有多少条"的展示 | **一律计入全部内容**（加密空间内条目、范围内的 Memo 与待办、单篇加密条目），**不因锁定 / 解锁改变**【已定·用户确认 2026-09-26】。这推翻了定稿 M08-07 与 §9.2 的"锁定时不显示条目数" |
| **搜索结果条数** | 搜索面板上的命中数 | 与本次结果**同源**（命中几条显示几条）——它是"这次搜索的结果数"，不是统计 |
| **MCP 计数** | `list_folders` 返回的条目数 | **不含**隐私内容，且空间节点不出现在 MCP 的文件夹树中（见 5.3、I4） |

配套口径：

1. 锁定时空间**仍不可展开**——只显示数量，看不到标题与正文；
2. **计数与列表可以不一致**（数字 12、列表 0 条），这是本次决定的已知后果并已接受；界面不得为此加"另有 N 条不可见"之类的补充文案；
3. 统计计数**不参与门禁判定**：实现上"算统计"的函数根本不接受解锁态入参，避免以后有人顺手加过滤。

## 五、可见性矩阵（两张，互不联动）

### 5.1 界面可见性（隐私锁状态 × 内容类别）

| 内容 | 隐私锁已锁定 | 隐私锁已解锁 |
|---|---|---|
| 加密空间节点 | 显示，**含条目数**，不可展开 | 可展开、可浏览（两层文件夹 + 列表/正文双栏） |
| 空间内条目 | 不出现在**任何列表、搜索与筛选结果**中；但**计入统计计数** | **进入最近编辑、收藏、标签视图**（解锁期间可见）＋ 加密空间内；正文可搜（受开关约束）；重锁后立即消失 |
| Memo 与待办（在范围内） | 两个视图整体占位；不进搜索 | 正常显示；可搜【定稿 M09-02】 |
| Memo（不在范围内） | 正常显示 | 正常显示 |
| 单篇加密条目 · 未解密 | 明文标题 + 锁标识，正文不渲染；**可按标题搜到**，搜不到正文 | **同左**（不受隐私锁解锁影响） |
| 单篇加密条目 · 已解密（本次会话） | 标题与正文都可搜（正文受开关约束）；正文可读、可编辑 | 同左 |
| 普通内容 | 正常显示、可搜 | 正常显示、可搜 |
| 快速录入框 | 可正常写 Memo（写入永远免密）【定稿】 | 可正常写 |

补充口径【已定·用户确认 2026-09-26】：

1. 单篇加密条目的**标题**（本就是明文可见的）**任何状态下都可被搜到**；正文只在**该篇已解密**后可搜。"解锁时可搜索加密内容"这一个开关**只管正文**——它作用于空间内条目的正文与已解密单篇的正文。
2. 单篇条目的正文可搜**不要求隐私锁处于解锁态**——该篇已逐篇解密即可（与机制二的独立语义一致）。
3. 空间内条目在**解锁期间**进入最近编辑、收藏、标签视图（含标签筛选）；重新锁定后立即消失——与加密空间同生共死。这推翻了原定稿 §9.1 的"任何时候都不出现"。
4. 列表与计数都来自本地元数据；锁定/解锁是一次**状态切换**，切换后立即重渲染，不留残影。

### 5.2 MCP 可见性（令牌配置 × 内容类别）

| 内容 | 对 MCP |
|---|---|

| Memo | 令牌勾选"包含 Memo"时可见；与隐私范围、隐私锁状态**都无关**【定稿 M17-01/03】；默认不勾选＝不可见 |

| 回收站中的条目 | 不可见（定稿里标【补全】，本文沿用） |

### 5.3 不变式（实现与测试必须守住）

- **I1**：MCP 可见集合 ＝ 令牌范围 ∩ 非隐私内容 ∩（Memo 需勾选"包含 Memo"）∩ 非回收站，且**与隐私锁是否解锁无关**。

- **I4**：MCP 返回的条目数不含隐私内容；空间节点不出现在 MCP 的文件夹树里。
- **I5**：服务端兜底搜索 `GET /api/search` **暂时也恒排除**隐私内容——不新增"是否解锁"参数，门禁判定只留前端一处。代价是"本地索引未建完"的兜底场景里隐私内容召回略低（界面已有索引提示）。**M3 实测本地索引召回后再定是否加参数**【待确认·实测后定】。

## 三、门禁判定契约与代码落点

### 3.1 判定要回答的四个问题

| # | 问题 | 谁在问 |
|---|---|---|
| 1 | 这条能不能出现在**列表与筛选结果**里 | 最近编辑 / 收藏 / 标签 / 首页最近动态 / 空间内的列表 |
| 2 | 这条的**正文**能不能渲染 | 编辑器、版本对比、导出 |
| 3 | 这条按**哪些字段**参与搜索命中 | 本地检索（标题/标签 vs 正文） |
| 4 | 这条**计不计数** | 首页统计、导航与文件夹计数、标签云 → **一律计入，不需要判定**（见 4.7） |

### 3.2 纯函数契约（`packages/shared/src/privacy.ts`）

放共享包的理由：前端判定用 JS、服务端过滤用 SQL，**两边必须同源**；共享包不依赖 `apps/*`，两端都能引。运行时状态不进共享包（见 3.6）。

```ts
export type PrivacyLockState = "disabled" | "locked" | "unlocked";
export interface PrivacyScope { memo: boolean }
export interface PrivacyGate {
  lockState: PrivacyLockState;
  scope: PrivacyScope;
  /** 本次浏览器会话内已逐篇解密的条目 id（单篇加密） */
  unlockedItems: ReadonlySet<string>;
  /** 设置项「解锁时可搜索加密内容」——只作用于**正文**命中 */
  searchBodiesWhenUnlocked: boolean;
}

export const DEFAULT_PRIVACY_SCOPE: PrivacyScope = { memo: true };

/** 带隐私标记的条目（空间内或单篇） */
export function isPrivacyItem(item: { enc_self: 0 | 1; in_enc_space: 0 | 1 }): boolean;

/** 该类内容是否属于隐私范围（space 恒 true；memo 看配置） */
export function isInPrivacyScope(kind: "space" | "memo", scope: PrivacyScope): boolean;

/** 问题 1：能否出现在列表/筛选结果里 */
export function canShowInList(item: ItemFlags, gate: PrivacyGate): boolean;

/** 问题 2：正文能否渲染（空间内看隐私锁，单篇看该篇是否已解密；两者兼有时都要满足） */
export function canReadBody(item: ItemFlags, gate: PrivacyGate): boolean;

/** 问题 3：按哪些字段参与搜索 */
export function searchFields(item: ItemFlags, gate: PrivacyGate): { title: boolean; body: boolean };

/** Memo 门禁（账户级）：视图整体占位时返回 false */
export function isMemoVisible(gate: PrivacyGate): boolean;
```

判定规则（`ItemFlags` = `enc_self` / `in_enc_space` / `deleted_at` / `tags`）：

| 类别 | 列表可见（问题 1） | 正文可读（问题 2） | 搜索：标题/标签 | 搜索：正文 |
|---|---|---|---|---|
| 普通内容 | 总是 | 总是 | ✓ | ✓ |
| 空间内条目 | 仅隐私锁**已解锁**时 | 仅已解锁时 | 仅已解锁时 | 已解锁 **且** 开关开 |
| 单篇加密条目 | 总是（标题明文） | 仅该篇**已解密**时 | **总是** | 该篇已解密 **且** 开关开 |
| Memo（在范围内） | 仅已解锁时（两个视图整体占位） | 仅已解锁时 | 仅已解锁时 | 已解锁 **且** 开关开 |
| Memo（不在范围内） | 总是 | 总是 | ✓ | ✓ |
| 回收站中的条目 | 不进普通列表 | — | ✗ | ✗ |

### 3.3 前端三处消费点

1. **列表与筛选**：`apps/web/src/features/notes/views.ts` 的筛选纯函数增加 `gate` 入参（`canShowInList`）；首页最近动态同源处理（见下方【待确认】）。
2. **搜索**：`apps/web/src/data/db/search.ts` —— 索引**照常包含隐私条目**，查询时按 `searchFields()` 过滤（改造细节见 3.5）。
3. **Memo / 待办 / 首页的锁占位**：`features/memos`、`features/tasks`、`features/home` 现在拿的是 `memoLocked` 恒 `false` 的 prop（`HomePanel`、`TodayTasks`、`RecentActivity`、`StatCards`），M3 改为传真实门禁值。

> 【已定·用户确认 2026-09-27】首页「最近动态」卡片：定稿"新增④"原文写"条目统计与**最近动态**始终计入加密空间内条目"，但最近动态是**带标题的列表**。**结论：计数一律计入、列表按门禁过滤**——锁定时不列空间内条目（避免露出标题），解锁后列入。即"最近动态始终计入"应读作**计数口径**，不是"列表照列"。

### 3.4 服务端一处（收敛，不加参数）

- 新增 `apps/worker/src/db/privacy.ts`，导出**唯一**的 SQL 片段：`privacyExcludeSql(alias = "i")` 与默认别名下的常量 `PRIVACY_EXCLUDE_SQL`（`i.enc_self = 0 AND i.in_enc_space = 0`；带别名是为了能直接拼进 `items` 查询，别名可由调用方指定）。现有的 `apps/worker/src/services/search.ts` 里的字面量改为引用它；M6 的 MCP 查询、M5 的分享与导出校验同样引用它。
- 配一条断言测试：服务端搜索语句里必须出现该常量（防止有人手写字面量后漂移）。**已落地**（2026-09-27，`apps/worker/test/search.test.ts`）。
- **I5 之下 M3 的服务端搜索行为不变**（仍恒排除隐私内容）——本次只是把两份实现收敛成一处。

### 3.5 搜索索引的改造（本次唯一要动地基的地方）

- 索引行**拆成两段文本**：`title_text`（标题 + 标签）与 `body_text`（正文），各自带 haystack/tokens。理由：新规则要求"标题可搜、正文按门禁"，单一合并文本做不到；而"锁定态不入索引、解锁时补索引"会在每次切换门户时重建全表，代价大且有时延。
- 索引**覆盖全部未删除条目**（含隐私条目）；`isSearchIndexComplete()` 的判定改为只看"未删除"，不再掺门禁。
- **Dexie 升版**：`searchIndex` 加列（`title_text` / `body_text` 及其 haystack/tokens）；`privacyState` 新表（见 5.1）。
- **M2 用例改写**：原"加密条目既不进索引也搜不到"改为四组断言——①进索引；②锁定态标题与正文都搜不到；③解锁态标题可搜、开关关闭时正文搜不到、开关打开时正文可搜；④单篇未解密标题可搜、正文搜不到。

### 3.6 结构护栏（feature 之间的依赖）

- **判定纯函数**放 `packages/shared`（两端可用，不引入 feature 依赖）。
- **运行时状态与界面件**放 `features/privacy/`（解锁框、锁定占位、胶囊状态、`model.ts` 的状态机）；其它 feature **只引共享包的纯函数**，`PrivacyGate` 对象由 `app/` 层组装后按 props 注入——沿用 M2 已确立的"`app/` 作插槽、feature 不互相依赖"模式。
- ESLint 里"前端 feature 互不依赖"目前**只是注释占位、没有规则**（`eslint.config.js` 末尾）。M3 把它落成**静态守卫测试**（读 `apps/web/src/features/**` 的 import 语句，断言不跨 feature），与 M2 的 `layout-invariants.test.ts` 同一条路子，**不新增依赖**。

## 四、`user_crypto` 权威 DDL 与迁移 0003

### 4.1 权威 DDL（迁移 `apps/worker/src/db/migrations/0003_user_crypto.ts`，导出 `{ version: 3, statements }`）

```sql
CREATE TABLE IF NOT EXISTS user_crypto (
  user_id            TEXT PRIMARY KEY,
  kdf                TEXT    NOT NULL CHECK (kdf IN ('PBKDF2-SHA-256')),
  kdf_iterations     INTEGER NOT NULL CHECK (kdf_iterations BETWEEN 100000 AND 2000000),
  kdf_salt           BLOB    NOT NULL,
  verifier           BLOB    NOT NULL,
  k_wrapped_pw       BLOB    NOT NULL,
  k_wrapped_backup   BLOB    NOT NULL,
  rev                INTEGER NOT NULL DEFAULT 1,
  created_at         INTEGER NOT NULL,
  updated_at         INTEGER NOT NULL
);
```

- **BLOB 自带版本号**（将来换算法不用改表）：`版本(1B) || IV(12B) || 密文 || GCM 标签(16B)`。
  - `verifier`：`AES-GCM(KEK, 常量 "menote-verifier-v1")`；
  - `k_wrapped_pw`：`AES-GCM(KEK, K)`（供外部解密工具，架构 §7.3 的信封块与此同构）；
  - `k_wrapped_backup`：`AES-GCM(BACKUP_CRED_KEY, K)`（供 Worker，架构 §12.4）；
  - `kdf_salt`：16 字节；`kdf_iterations`：600,000（`PBKDF2-SHA-256`，与登录 KDF 共用实现）。
- **不存**明文 K、KEK、隐私密码或其裸哈希（除 verifier）。
- **不加 `sync_seq`**：与《同步引擎设计》§7 的推荐一致——门禁材料走专用端点，不混进普通同步载荷（因此 M3 不改 M1 的同步协议）。
- 迁移登记：`db/selfheal.ts` 的 `MIGRATIONS` 数组 + `REQUIRED_TABLES`（无新索引）。
- **不建** `data_keys` / 密文列 / `convertJobs`（v1.1 模型修订已取消）；`items`、`folders` 的标记列 M1 已建，**本次不动热表**。

### 4.2 端点（`routes/crypto.ts` + `services/crypto.ts`）

| 端点 | 用途 | 备注 |
|---|---|---|
| `GET /api/crypto` | 取门禁材料：`enabled` / `materials`（`kdf` / `kdf_iterations` / `kdf_salt` / `verifier` / `k_wrapped_pw` / `k_wrapped_backup`）/ `rev` / `updated_at` | 需会话鉴权；`Cache-Control: no-store`；**二进制一律 base64url**（复用 shared 的 `base64url.ts`，与登录密钥、会话令牌同一套编码——比设计初稿写的 standard base64 更省一次转换） |
| `PUT /api/crypto` | 启用 / 改密 / 重置后写入全部字段（**服务端校验 BLOB 长度与格式版本**，不合格 422） | 后写为准，`rev + 1`；响应不回显材料之外的任何东西 |
| `POST /api/crypto/reset` | 忘记隐私密码：服务端用 `BACKUP_CRED_KEY` 解包 K 并返回明文 K（base64url） | `no-store`；**不得写入日志或审计正文**；浏览器用完即弃；缺机密时只让这一条路 503 |
| `DELETE /api/crypto` | 关闭隐私锁 | **服务端校验"无隐私内容"**：`items` 中 `enc_self = 1 OR in_enc_space = 1` 的条数 > 0（**含回收站中的条目**）→ **422 `invalid`** 并返回 `detail: { reason: "privacy_content_exists", count }`（设计初稿写 409；现有错误码表里没有"状态冲突"这一类，新增错误码属 API 契约变更，留到需要时统一加，故先用 422） |

### 4.3 新增 Worker 机密（**属"先确认再动"区，需你点头**）

- 新增机密 **`BACKUP_CRED_KEY`**：原计划 M5，按"`user_crypto` 一次建全"提前到 M3。用途：解包/包裹 K（重置流程现在就要用；Cron 备份加密 M5 用）。
- 派生：`SHA-256(机密字节)` → 32 字节 AES-GCM 密钥（避免 base64 解码差异）。
- 落地清单：`.dev.vars.example`（注释从"M5"改为"M3"）、部署页机密项、`apps/worker/src/types.ts` 的 `EnvBindings`、`apps/worker/vitest.config.ts` 的 miniflare 绑定（否则测试跑不起来）。
- **轮换风险**：更换该机密 → 已存的 `k_wrapped_backup` 解不开 → 解锁态下重新包裹一次即可修复。写进运维注意项（Runbook 属 M6）。

## 五、会话态、多标签与档位计时

### 5.1 状态放哪

| 状态 | 存放 | 生命周期 |
|---|---|---|
| 隐私锁解锁态 | 内存（`features/privacy/model.ts` 单例 + hook） | 由档位决定；随标签页存在 |

| 单篇已解密集合 | 内存（会话态） | 本次浏览器会话；关闭标签页即失效 |
| verifier 与 K 包裹的本地缓存 | Dexie 新表 `privacyState` | 支持离线解锁；是否随登出清除见 **Q22【待确认】**（第十章落地） |

### 5.2 多标签一致性

- 复用 M2 的 BroadcastChannel（`menote` 前缀，`data/sync/broadcast.ts`），新增事件：`privacy-unlocked`（带档位与到期时间）、`privacy-locked`、`item-unlocked` / `item-locked`（**只放 id，不放内容**）。
- **新标签页握手**：加入时先发 `privacy-state-request`，已有标签页回一次当前状态；无人应答说明本次会话还没有解锁态 → 视为锁定（与"所有标签页关闭即锁"一致）。
- 任一处锁定 → 广播 → 其它标签页立即锁定并重渲染。

### 5.3 本模型下**不再需要**的东西

- 不监听 `visibilitychange` / `pagehide` 做锁定（"标签页隐藏即锁"已作废）；这两个事件不承担门禁语义。
- 不需要 SharedWorker、不需要持久化不可导出的 CryptoKey、不需要撤销 `blob:` 地址。
- 锁定时的"清理清单"缩减为界面项：关闭明文视图 → 切占位 → 清内存态（仅"锁全部"时清单篇已解密集合）。

### 5.4 "立即锁定"的两级语义

- 顶栏胶囊「立即锁定」= **锁全部**（隐私范围 + 清单篇已解密集合）【本文决定】；
- 编辑器/锁标识上的「锁上此篇」= 只清该篇；
- 列表/空间上的「锁上全部单篇」= 只清单篇集合，不动隐私锁；
- 「锁定此设备」= 锁全部 + 清 `localStorage` 的设备长期标记。

### 5.5 N 分钟计时

- 活动事件（`pointerdown` / `keydown` / 滚动）刷新到期时间；用一个 `setTimeout` 到点触发，**不轮询**。
- 标签页隐藏期间计时照走（机器闲置也会锁），这是"无操作 N 分钟"的字面语义。
- 倒计时剩 30 秒：胶囊闪烁一次 + 编辑器状态栏提示（文案见第九章）。

## 六、加密空间内置行

### 6.1 行的形状

`is_enc_space = 1`、`parent_id = NULL`、`in_enc_space = 0`、`name = '加密空间'`、`depth = 0`、`position = 0`、`meta_rev = 1`、`sync_seq = <按 M1 规则分配>`、`id = 服务端新 ULID`、`created_at` / `updated_at`。

M1 已就位的约束直接生效：`CHECK (is_enc_space = 0 OR (depth = 0 AND parent_id IS NULL AND in_enc_space = 0))` 与部分唯一索引 `idx_folders_enc_space ON folders(user_id) WHERE is_enc_space = 1`。

### 6.2 创建与自愈补建

- `services/folders.ts` 新增 `ensureEncSpace(db, userId)`：先 `SELECT`；缺失则 `INSERT OR IGNORE`（含 sync_seq 分配，沿用 M1 的计数器写法）；被唯一索引拦下（并发补建）则重读返回。
- 调用点：**注册成功**与**登录成功**（都在 `routes/auth.ts` 的服务路径上）——一次覆盖新用户与 M1/M2 存量账号；**不在读路径**（`GET /api/sync`）里写数据。
- **客户端 UI 不依赖该行存在**：`VaultNode` 恒显示（未启用时"未启用"、锁定时显示计数但不可展开）；该行只用于挂载空间内条目与空间内文件夹。
- 该行**永不被删除**：服务端拒绝删除 `is_enc_space = 1` 的记录；关闭隐私锁也不删行（空间始终存在，M08-02）。

### 6.3 空间内的结构

- 移入空间根目录 = 一条 `patch_meta`：`folder_id = <空间行 id>` + `in_enc_space = 1`；
- 空间内文件夹：`parent_id = <空间行 id>`、`depth = 1/2`、`in_enc_space = 1`（两层上限与普通文件夹同一套校验）；
- 空间内新建的条目天然带标记（客户端创建时置 `in_enc_space = 1`，无需勾选）；
- 重命名空间：走 M2 已有的文件夹改名路径（`PATCH /api/folders/:id` + `meta_rev`），入口挂在空间节点的「更多」菜单。

## 十、离线与缓存失效

### 10.1 缓存什么

Dexie 新表 `privacyState`（单行，`key = "user"`）：`enabled` / `kdf` / `kdf_iterations` / `kdf_salt` / `verifier` / `k_wrapped_pw` / `k_wrapped_backup` / `rev` / `updated_at`。服务端 `user_crypto` 是唯一权威，本地只是缓存。

### 10.2 何时写、何时读

- **首次与每次启动**：登录后（或同步启动时）`GET /api/crypto` 一次；写入本地缓存。
- **写入路径**：启用 / 改密 / 重置 / 关闭成功后，用响应覆盖本地缓存。
- **解锁**：优先用**本地** verifier 校验（离线可用）；本地缺失 → 必须联网。
- **失效检测**：若服务端 `rev` 高于本地 → 覆盖本地，并**清空内存解锁态与已解密集合**（密码在别处改过，旧状态无效）。
- **换设备**：首次登录没有缓存 → 联网取材料后解锁。

### 10.3 离线边界

| 场景 | 行为 |
|---|---|
| 有缓存 + 离线 | 可解锁、可锁定、可见性正常 |
| 无缓存 + 离线 | 提示"需要联网校验隐私密码"；保持锁定（不做任何"放宽"） |
| 启用 / 改密 / 重置 / 关闭 + 离线 | 入口置灰并说明需要联网 |
| 解锁后离线编辑 | 正常（内容明文，照常进 outbox；无密钥操作） |

### 10.4 Q22（登出是否清除本机缓存）的处置【本文决定】

- M3 **不新增登出询问**——Q22 整体仍未决，归 M6 的「数据管理」一并定；
- 但 `privacyState` **纳入"清除本机数据"的清单**（M6 落地时一并清），现在就写进清单以免漏；
- 登出时清空**内存**解锁态与已解密集合（它们本就是会话态）；
- 若日后决定"登出即清隐私材料"，只需把 `privacyState` 加入登出清理清单，**不需要改本设计**。
