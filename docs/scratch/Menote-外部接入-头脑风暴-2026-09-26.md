## 一、目标与原则【讨论】

**目标**：在 Web 版之外，通过五个渠道使用 Menote：手机上的客户端、浏览器插件剪藏网页、Obsidian 插件推送笔记、AI Agent 读写笔记、Telegram 机器人快速记 Memo。

**原则**：

1. **一套接口、一套令牌**。五个渠道共用同一个服务端和同一套令牌体系。令牌在 v7.4 §17.3 的 MCP 令牌基础上扩展，不另起一套。【待定 D1】
2. **规则不因渠道而变**。外部写入和网页里的编辑走同样的规则：有版本、进回收站、冲突不覆盖。【已有 §14、§17.4】
3. **加密内容对插件、AI Agent、机器人一律不可读**，和 v7.4 §6.13 对 MCP 的规定一致。移动端客户端例外，它等同网页登录，在设备上用隐私密码解开。浏览器插件可以“只写”进加密空间，靠之前定的账户公钥机制，插件本身拿不到隐私密码。【待定 D3】
4. **最小权限**。插件和机器人只拿到完成任务所需的权限；只有移动端和 AI Agent 才可能拿到读权限。【开发经理】
5. **家人互相隔离**。每个人只能用自己的令牌写自己的内容，owner 也不例外。【已有 §17.3】
6. **不增加 D1 负担**。内容没变就不写，Obsidian 批量推送要分批。【开发经理】

## 三、五个渠道共用的产品规则【讨论】

### 3.1 两类令牌

| | 客户端令牌 | 接入令牌 |
|---|---|---|
| 用于 | 移动端客户端 | 浏览器插件、Obsidian 插件、AI Agent、Telegram 机器人 |
| 怎么来 | 在客户端里用账号密码登录后自动签发，一台设备一个 | 在设置里手动创建，复制给对应工具；Telegram 在绑定时自动生成 |
| 能力 | 等同网页登录：同步全部内容，加密内容以密文同步，在设备上解开 | 按权限勾选；加密内容一律不可读 |
| 管理 | 设备管理页：设备名、最近使用、远程登出 | 令牌管理页：沿用 §17.3 的命名、权限、范围、过期、审计、撤销 |

### 3.2 接入令牌的权限（在 §17.3 基础上扩展）

v7.4 §17.3 的权限是：只读（始终包含）、新建和追加、修改和移动、移到回收站，外加文件夹范围和“包含 Memo”。本稿建议补三处：

1. **允许“只写不读”**。浏览器插件、Obsidian 插件、Telegram 机器人只需要往里写。令牌泄露时，只写令牌最多被塞进垃圾内容，看不到已有内容。这一条要改 §17.3 的“只读始终包含”。【待定 D2】
2. **新增“写入加密空间”权限**，默认关闭，单独勾选。只能往加密空间根目录新建，不能读、不能改、不能移动。第一期只给浏览器插件用。【待定 D3】
3. **创建令牌时选渠道类型**（AI Agent、浏览器插件、Obsidian 插件；Telegram 自动生成），界面按渠道预填推荐权限，减少家人配错。具体默认权限见 7.2.2。

### 3.3 设备管理

- 设置里新增“设备管理”页，列出网页会话、移动端设备和接入令牌：名称、类型、最近使用时间，并可一键撤销。
- 手机丢失：远程登出后，该设备再联网时立即清空本地数据库和缓存。离线状态下做不到，界面要如实说明。【开发经理】
- 这让功能拆解里的 M01-06“登录设备与会话管理”（目前是“后续定”）变成外部接入的前提。

### 3.4 写入规则（各渠道一致）

| 规则 | 说明 | 来源 |
|---|---|---|
| 新建不重复 | 同一次新建重试多次，只生成一条 | 【已有 §17.4】 |
| 修改带版本号 | 版本对不上就返回冲突，不静默覆盖 | 【已有 §17.4】 |
| 修改前封存版本 | 外部修改正文前先封存当前稿，改动都能在版本历史里撤回 | 【已有 §17.4】 |
| 内容没变不写 | 和当前版本完全相同就什么都不写，不产生版本 | 【开发经理】 |
| 删除只进回收站 | 外部渠道最多“移到回收站”，永久删除不开放 | 【已有 §17.3】 |
| 大小上限 | 单条约 2MB 的上限在客户端或插件一侧就先拦下 | 【已有 §10.10】 |
| 创建时间 | Memo 的创建时间在新建时定下，服务端只保存、不改写，同步时也不覆盖 | 【开发经理】 |

## 四、各渠道要点【讨论】

### 4.1 移动端

**路线**（开发经理的分析，待你定 D6）：

1. **PWA**：网页加上 manifest 和 Service Worker 后可以添加到主屏、离线打开；安装后系统分享菜单里会出现 Menote，分享文字直接生成 Memo。分享图片要等附件功能做好。【开发经理】
2. **可选：TWA 打包**：一个很薄的安卓壳，网页更新 App 就跟着更新。缺点是和手机 Chrome 共用登录与数据；手机上没有 Chrome 时会退回系统 WebView，行为不同。【开发经理】
3. **原生客户端（Capacitor 加共享核心）**【开发经理推荐】：同步引擎、加密、Markdown 解析抽成共用包，网页和安卓共用一份。
   - 第一期：功能和网页一致，加上系统分享、断网打开。
   - 第二期：桌面小组件、提醒通知、指纹解锁。
   - 更新：网页部分可以热更新，下次打开生效，资源包要做签名校验；只有原生部分变了才需要重装。【开发经理】

**要定的产品规则**：

- 手机丢失的处理，见 3.3。
- Memo 在本地是明文存储（§8.9），手机丢了可能被读出来，界面上要说明。
- “当前设备长期”解锁档位在手机上怎么处理。【待定 D9】
- 窄屏布局目前没有设计，原生客户端之前要先补一套窄屏布局与交互。

### 4.2 浏览器插件

- 弹窗里只放三样：存成 Memo 还是笔记、目标文件夹、标签。
- 选中一段文字存成 Memo，剪整篇文章存成笔记，自动附上原文链接和剪藏时间。【开发经理】
- 默认存到哪里。【待定 D11】
- 同一个网址再剪一次，提示“更新原来那篇，还是另存一篇”，不悄悄生成重复笔记。
- 可以存进加密空间：插件只用公钥加密，落在空间根目录，存完就看不见。存进加密空间的剪藏不查重，原文网址和剪藏时间放进密文，否则服务器上的网址会暴露你剪了哪些页面。【开发经理】
- 图片：下载后上传到 R2，避免原网页删图或防盗链导致打不开；存进加密空间时图片也要加密，放第二期。【开发经理】
- 权限只申请“当前标签页”和 Menote 自己的域名；只给家人用时可以不上架商店，直接加载扩展。【开发经理】

### 4.3 Obsidian 插件

- **先单向**，只从 Obsidian 推到 Menote：【开发经理】
  - 第一步：推送单篇和文件夹，冲突时让用户选择。
  - 第二步：文件夹持续映射，推送前列出“将新增 N 篇、更新 M 篇、删除 K 篇”，确认后执行。
  - 第三步：再看需不需要从 Menote 拉回来。整库双向映射暂不做。
- 推送过来的笔记默认只读，或编辑时提醒，让 Obsidian 当唯一的修改来源。【待定 D5】
- 只读要留出口：可以“断开与 Obsidian 的关联”，变成普通笔记；插件下次推送时提示重新关联还是新建一篇。【开发经理】
- 插件只能改它自己推送过来的笔记，碰不到你在 Menote 里自己写的内容（7.2.2 的“只能改自己建的条目”）。【开发经理】
- Obsidian 里删除，Menote 这边只进回收站。
- 没改过的笔记不推送、不记版本。【开发经理】
- 只推送成笔记，不推送成 Memo 或表格；Obsidian 的标签对应成 Menote 标签。
- 映射关系存在插件自己的数据里，不往你的笔记里写东西。【开发经理】
- 推送目标是加密内容时，第一期直接拒绝并提示。
- Obsidian 特有语法（双链、嵌入、提示框、高亮、注释）怎么处理。【待定 D10】

### 4.4 AI Agent（MCP）【已有 §17】

- 沿用 v7.4 §17：固定地址、令牌走请求头、11 个工具、加密内容不可见、永久删除不开放。
- 本稿唯一的变化：MCP 令牌并入“接入令牌”统一管理。【待定 D1】

### 4.5 Telegram 机器人

- 给机器人发文字，存成一条 Memo；发图片，存成带图片的 Memo。存完回复“已保存”。【开发经理】
- 每个家人在 Menote 设置里生成一次性绑定码，在 Telegram 里发给机器人完成绑定，之后只接受绑定过的私聊，群组消息一律忽略。【开发经理】
- 机器人只能新建 Memo，不能读、不能改、不能删，也不能写入加密空间。【开发经理】
- 在中国大陆，手机上使用 Telegram 需要自行解决网络访问。【待定 D8】

## 七、共用接口【开发经理补写，讨论】

> 本章只覆盖用户确定的五个渠道：移动端、浏览器插件、Obsidian 插件、AI Agent（MCP）、Telegram 机器人。
> 本章全部内容都是讨论稿，未经确认。涉及需要修改设计文档 v7.4 的地方，统一列在 7.10。

### 7.1 总体形态

五个渠道分成三类，走三个入口，但共用同一个 Worker、同一套服务层和同一套写入规则：

| 入口 | 谁在用 | 认证方式 | 说明 |
|---|---|---|---|
| `/api/v1/sync/*` 同步接口 | 移动端客户端 | 客户端令牌（`Authorization: Bearer`） | 和网页现有的同步接口（项目架构 §6.1）是同一组处理逻辑，只是换成令牌认证、路径加上版本号。网页继续用 `/api/*` 和 Cookie，路径不变 |
| `/api/v1/ingest/*` 接入接口 | 浏览器插件、Obsidian 插件 | 接入令牌（`Authorization: Bearer`） | 只提供写入相关的少数几个接口：新建、更新、移到回收站、上传附件、取公钥 |
| `/mcp` | AI Agent | 接入令牌 | 保持 v7.4 §17 原样，不改工具集 |
| `/hooks/telegram` | Telegram 机器人 | Telegram 的 Webhook 密钥 + 账号绑定 | Telegram 服务器把消息推给 Worker，Worker 在服务端直接调用服务层写入，不经过上面的 HTTP 接口 |

原则：
- 所有入口最终都落到同一个服务层，版本、回收站、冲突、大小上限、加密内容不可见这些规则只实现一份。
- 带 `Authorization` 请求头的请求一律忽略 Cookie，也不做 CSRF 校验（没有 Cookie 就不存在 CSRF）；带 Cookie 的请求照旧校验 `X-Menote` 和 `Origin`。两种认证不混用。

### 7.2 令牌

#### 7.2.1 客户端令牌（移动端）

| 项 | 设计 |
|---|---|
| 签发 | 客户端走和网页相同的 `prelogin` / `login` 流程（登录密钥在客户端派生），请求里多带设备名和平台；登录成功后返回一个客户端令牌，不下发 Cookie |
| 格式 | `mnc_` 前缀 + 32 字节随机数的 base64url；库里只存 SHA-256 哈希，和 §17.3 的做法一致 |
| 校验 | 每个请求查一次库，等同于网页会话；因此撤销立即生效，不需要短期令牌加刷新令牌那一套 |
| 过期 | 90 天没有使用自动失效；正常使用时不过期 |
| 存放 | 安卓上存进 Android Keystore 保护的安全存储，不放在普通的 WebView 存储里 |
| 最近使用 | `last_used_at` 每天最多写一次，和网页会话一样 |
| 撤销后 | 服务端返回 `401 device_revoked`；客户端收到后清空本地数据库、缓存和令牌，回到登录页 |
| 能力 | 等同网页登录：可以同步全部内容，加密内容以密文同步，在设备上用隐私密码解开 |

新增表 `devices`：`id`、`user_id`、`name`、`platform`、`app_version`、`token_hash`、`created_at`、`last_used_at`、`revoked_at`。设备管理页同时列出网页会话和客户端设备。

#### 7.2.2 接入令牌（浏览器插件、Obsidian 插件、AI Agent、Telegram 机器人）

沿用 v7.4 §17.3 的令牌表和全部规则（`mn_` 格式、只存哈希、只显示一次、文件夹范围、包含 Memo、过期、审计、撤销、限速、每人最多 20 个），在上面增加以下字段：

| 新增字段 | 取值 | 作用 |
|---|---|---|
| `channel` | `mcp` / `browser` / `obsidian` / `telegram` | 渠道类型。决定这个令牌能用哪个入口：`mcp` 只能用 `/mcp`，`browser` 和 `obsidian` 只能用 `/api/v1/ingest/*`，`telegram` 不能通过 HTTP 使用（只在服务端内部使用） |
| 权限位 | 读 / 新建 / 修改 / 移到回收站 / 写入加密空间 | 把“读”也变成可选项，用一个整数按位存储 |
| `own_items_only` | 0 / 1 | 为 1 时，“修改”和“移到回收站”只能作用于这个令牌自己新建的条目。Obsidian 插件用它，保证插件改不到用户在 Menote 里自己写的内容 |
| `default_target` | Memo，或某个文件夹 ID | 新建时不指定位置就落在这里 |

各渠道的默认权限（创建令牌时按渠道预填，用户可以改）：

| 渠道 | 读 | 新建 | 修改 | 回收站 | 写入加密空间 | 其他 |
|---|---|---|---|---|---|---|
| AI Agent | ✓ | 按需 | 按需 | 按需 | ✗ | 与 v7.4 §17.3 相同 |
| 浏览器插件 | ✗ | ✓ | ✓（仅自己建的，用于“更新原来那篇”） | ✗ | 可选 | `own_items_only = 1` |
| Obsidian 插件 | ✗ | ✓ | ✓ | ✓ | ✗ | `own_items_only = 1`，范围限定到映射的文件夹 |
| Telegram 机器人 | ✗ | ✓ | ✗ | ✗ | ✗ | 只能新建 Memo |

只写令牌的两条硬规则：
- 响应里只返回 ID、`rev`、内容哈希这类元数据，**不返回任何正文**。发生冲突时同样只返回服务端当前的 `rev` 和哈希。
- 查重（比如浏览器插件判断网址是否剪过）只回答“有没有、对应哪个 ID”，不返回标题或内容。

### 7.3 接口版本规则

- 路径里带大版本号：`/api/v1/...`。
- **兼容变更不升版本**：新增接口、新增可选字段、新增错误码。客户端必须忽略不认识的字段。
- **不兼容变更升到 v2**：删除或改名字段、改变字段含义、可选字段改成必填、改变错误语义。v1 和 v2 并存，v1 至少保留 6 个月，并且要等设备管理页里所有设备都升级之后才下线。
- **客户端版本上报**：每个请求带 `X-Menote-Client: <渠道>/<版本>`，例如 `android/1.2.0`、`obsidian/0.3.1`。
- **最低版本**：服务端按渠道维护最低支持版本。低于它时返回 `426 client_outdated`，附带提示文字和下载地址，客户端显示“版本过低，请更新”。
- **契约只写一份**：接口的请求和响应结构用 Valibot 定义在共用包里（建议 `packages/api-contract`），服务端用它校验，TypeScript 客户端从它生成类型。移动端、浏览器插件、Obsidian 插件共用一个接口客户端包（建议 `packages/client`）。Telegram 机器人在服务端运行，直接调用服务层，不需要这个包。

### 7.4 写入与冲突规则

和 v7.4 §15、§17.4 保持一致，这里只写外部接口上的具体形态。

**新建**
- 客户端生成条目 ID，同一个 ID 重复提交是幂等的（与网页一致）；接入接口另外要求 `operation_id`，服务端保留 7 天（§17.4）。
- 请求体直接是正文原文（`text/markdown`，加密时为 `application/octet-stream`），元数据放在请求头 `X-Menote-Meta` 里（与项目架构 §6.1 一致），避免 Worker 解析 2MB 的 JSON。
- 可以带一个**外部引用** `external_ref`：Obsidian 插件用它存“库里的文件标识”，浏览器插件用它存原文网址的哈希。服务端按 `(user_id, channel, external_ref)` 建唯一索引，用来查重和找到“原来那篇”。
- 写入加密空间的内容**不允许带外部引用**，否则服务端能看出剪了哪些网页。

**更新**
- 必须带 `If-Match: <rev>`。版本对不上返回 `409 rev_conflict`，附带当前 `rev` 和内容哈希，不静默覆盖。
- 大于 64 KB 的正文可以按 §15.7 走增量补丁；插件场景一般整篇提交就够了。
- 修改正文前按 §17.4 先封存当前稿为版本（同一条目 10 分钟内最多一次）。

**内容没变就不写**
- 请求头带 `X-Menote-Hash`（正文的 SHA-256，由客户端计算）。服务端和已存的内容哈希一比，相同就直接返回 `200` 和 `unchanged: true`，不写库，也不产生版本。
- 服务端不自己重算 2MB 正文的哈希（Worker 每个请求只有 10 ms CPU），与 §15.7 的做法一致。

**删除**
- 外部渠道最多只能“移到回收站”，永久删除不开放（§17.3）。

**大小**
- 单条硬上限 1,900,000 字节，超出返回 `413 too_large`。客户端和插件在提交前自己先检查，不等服务端报错。
- MCP 单次写入 256 KB 的限制保持不变（§17.4）；接入接口按全文上传，上限就是单条上限。

**创建时间**
- Memo 的 `created_at` 由客户端在新建时确定，服务端只保存，不改写；同步合并时也不覆盖。

**错误码**：沿用项目架构 §4.3，新增以下几个：

| HTTP | code | 含义 |
|---|---|---|
| 401 | `device_revoked` | 客户端令牌已撤销，客户端清空本地数据 |
| 401 | `token_invalid` | 接入令牌不存在、已过期或已撤销 |
| 403 | `scope_denied` | 权限不够，或者目标不在令牌范围内 |
| 426 | `client_outdated` | 客户端版本低于最低支持版本 |

### 7.5 附件上传

- 流程沿用项目架构 §8：客户端先算 SHA-256，询问服务端哪些已经存在，只上传缺的；上传是流式请求体，R2 用这个哈希校验完整性，Worker 不自己算哈希。
- 上传成功后客户端拿到附件地址（`/api/attachments/h/<sha256>`），把正文里的图片引用换成这个地址，然后再提交正文，同时在 `X-Menote-Refs` 里上报引用。先传附件、后提交正文，保证正文里不会出现打不开的图片。
- 上限建议：单个附件 20 MB（§14.1）；每次写入最多 30 个附件，超出的保留原链接并在结果里提示。图片由客户端先压缩再上传。
- 加密条目的附件由客户端先用该条目的数据密钥加密，再以随机 ID 上传（`e/{user_id}/{id}`，§14.1），不做哈希去重。
- Telegram 发来的图片由 Worker 从 Telegram 下载后流式写进 R2。因为 Worker 没有 CPU 预算去计算整个文件的哈希，这类附件用随机 ID 存储、不去重。Telegram 机器人接口本身限制下载文件不超过 20 MB。【待核实：Worker 流式转存时的实际 CPU 消耗】

### 7.6 加密写入（公钥）

用于“锁定时移入加密空间”（功能拆解 M08-09），浏览器插件写入加密空间也用这一套。

**账户密钥对**
- 算法：ECDH P-256。选它是因为浏览器、安卓 WebView、Obsidian（Electron）、浏览器插件里的 WebCrypto 都原生支持，不需要额外的库。
- 公钥明文存储，锁定时也能用；私钥用主钥 MK 包裹后存储（M08-09）。
- 新增表 `user_keypairs`：`user_id`、`key_id`、`public_key`、`private_key_wrapped`、`created_at`。

**包裹一把数据密钥（DEK）的方式**
1. 客户端临时生成一对 P-256 密钥，和账户公钥做 ECDH，得到共享密钥。
2. 用 HKDF-SHA256 从共享密钥派生出包裹钥，`info` 里写入条目 ID 和账户密钥的 `key_id`。
3. 用这把包裹钥以 AES-KW 包裹该条目新生成的 DEK。
4. 存储格式：格式版本（1 字节）+ 账户密钥 `key_id`（16 字节）+ 临时公钥（65 字节）+ 包裹后的 DEK（40 字节）。

**正文、标题、附件**
- 正文、附件都用这把 DEK 加密，沿用项目架构 §7.3 的密文信封格式和 §7.2 的 AAD 规则。
- 锁定时拿不到空间密钥，所以标题也先用这把 DEK 加密。下次解锁时，客户端用 MK 解开私钥，再解开 DEK，把标题改成用空间密钥加密，并把 DEK 改成由 MK 包裹，和其他条目保持一致（M08-09）。

**接口流程**
1. `GET /api/v1/ingest/public-key`：返回账户公钥和它的指纹。需要令牌有“写入加密空间”权限。
2. 客户端生成条目 ID 和 DEK，在本地加密正文、标题和附件。
3. 提交新建请求，标明“加密空间根目录”，附上包裹后的 DEK。
4. 服务端检查：令牌有写入加密空间的权限；目标是空间根目录；密文头部的格式版本和 `key_id` 与账户公钥一致；请求里没有外部引用。服务端解不开密文，也无法验证内容，最坏情况是被写进一条垃圾条目，可以靠来源标识找出来删掉。

**防止公钥被调包**
- 插件第一次取公钥时记下指纹，以后每次都比对，指纹变了就停止写入并提示用户。设置页显示公钥指纹，用户可以对照。这样即使服务器被攻破、公钥被换掉，插件也不会悄悄用攻击者的公钥加密。

**共用加密包**
- 在现有的 `packages/crypto-format` 旁边增加 `packages/crypto`：只依赖 WebCrypto，不依赖任何浏览器或 Worker 专有的 API。网页、移动端、浏览器插件、Obsidian 插件共用这一份代码，不各写一份。

**各渠道的加密能力**

| 渠道 | 读加密内容 | 写入加密空间 |
|---|---|---|
| 移动端 | 可以，在设备上用隐私密码解开 | 可以，和网页相同 |
| 浏览器插件 | 不可以 | 可以（公钥） |
| Obsidian 插件 | 不可以 | 第一期不做，推送目标是加密内容时直接拒绝 |
| AI Agent | 不可以（§6.13） | 不可以 |
| Telegram 机器人 | 不可以 | 不可以。消息内容本来就经过 Telegram 的服务器，服务端再加密意义不大 |

### 7.7 跨域与认证

| 渠道 | 请求从哪里发出 | 需不需要 CORS | 令牌存在哪里 |
|---|---|---|---|
| 网页 | 同源 | 不需要 | Cookie |
| 移动端（Capacitor） | App 内的 WebView，源是 `https://localhost` | 优先用 Capacitor 的原生 HTTP 插件发请求，这样不受 CORS 限制；如果用 WebView 的 fetch，就要给 `/api/v1/sync/*` 配 CORS 白名单 | Android Keystore 保护的安全存储 |
| 浏览器插件 | 插件的后台脚本 | 不需要：插件声明了 Menote 域名的权限后，后台脚本发请求不受 CORS 限制。**只在后台脚本里调接口，不在注入网页的脚本里调** | `chrome.storage.local`（不用 `storage.sync`，避免令牌同步到浏览器账号） |
| Obsidian 插件 | Obsidian 的 `requestUrl` | 不需要，`requestUrl` 不受 CORS 限制 | 插件的 `data.json`。**它放在库目录里，会随库同步到网盘或 Git**，所以 Obsidian 令牌只给映射文件夹的权限，界面上要提醒 |
| AI Agent | 服务器或本机进程 | 不需要 | Agent 自己的配置 |
| Telegram 机器人 | Telegram 服务器调用 Worker | 不需要 | 机器人令牌存为 Worker Secret |

CORS 规则（只在确实需要时开启）：
- 只对 `/api/v1/sync/*` 开放，只允许白名单里的源（`https://localhost` 等 Capacitor 用的源）。
- 不返回 `Access-Control-Allow-Credentials`，也就是不允许跨域带 Cookie，外部只能用 Bearer 令牌。
- `/api/*`（网页接口）和 `/mcp` 不开 CORS。

### 7.8 Telegram 机器人

- **一个部署一个机器人**：机器人令牌存为 Worker Secret `TELEGRAM_BOT_TOKEN`，owner 在部署时配置。
- **Webhook 校验**：用 Telegram 的 `setWebhook` 设置一个随机的 `secret_token`，Telegram 每次推送都会带上 `X-Telegram-Bot-Api-Secret-Token` 请求头，Worker 校验不通过就直接拒绝。这个值同样存为 Worker Secret。
- **账号绑定**：用户在 Menote 设置里点“绑定 Telegram”，得到一个 10 分钟内有效的一次性绑定码；在 Telegram 里给机器人发 `/bind <绑定码>`。服务端记下 Telegram 用户 ID 和 Menote 用户的对应关系，同时为它生成一个 `channel = telegram` 的接入令牌（只能新建 Memo），权限、审计、撤销都走接入令牌那一套。
- **只接受绑定过的私聊**：未绑定的用户、群组里的消息一律忽略，只回一句“请先在 Menote 里绑定”。
- **防重复**：Telegram 在收不到 `200` 时会重试同一条消息，所以用 `tg:<update_id>` 作为 `operation_id`，重复推送不会生成两条 Memo。Worker 尽快返回 `200`。
- **支持的内容**：文字存成 Memo；图片存成带附件的 Memo（见 7.5）。存完回复“已保存”。
- **新增表** `telegram_bindings`：`telegram_user_id`、`user_id`、`token_id`、`created_at`。
- **可达性**：Worker 在 Cloudflare 上调用 Telegram 没有问题；但在中国大陆，手机上使用 Telegram 需要自行解决网络访问。

### 7.9 限速与 D1 额度

- 接入令牌：沿用 §17.3，每个令牌默认每分钟 60 次。
- 客户端令牌：和网页会话一样不单独限速，但同步拉取本来就按游标分页。
- **Obsidian 批量推送**：插件每个请求最多提交 20 篇，一批一批按顺序发；遇到 `429` 按 `Retry-After` 等待，遇到 `503` 就暂停，下次再从中断处继续。没改过的笔记在插件本地用哈希先筛掉，服务端再用“内容没变不写”兜底。
- **少写库**：`last_used_at` 接入令牌最多每 10 分钟写一次（§17.3），客户端设备每天最多一次；审计记录和写入放在同一个 D1 batch 里，不单独多发请求。
- **额度提醒**：Cloudflare 从 2026-09-01 起严格执行 D1 免费版的每日读写上限，超出后当天的查询会失败。批量推送前，插件先显示“将新增、更新多少篇”，让用户确认，避免一次推送用光当天的写入额度。
